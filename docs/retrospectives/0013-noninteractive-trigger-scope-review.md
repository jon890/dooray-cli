# 비대화형 진입 조건과 조합 옵션의 범위 구분

## 관찰

독립 코드 검토의 최초 판정은 참여자 옵션과 `--mention`, `--link-task`, `--parent`를 함께 전달하면 범위 밖 옵션도 비대화형으로 처리된다는 이유로 `FIX_NEEDED`였다.

## 원인

범위 밖 계약인 “mention/link/parent 단독 호출 지원”을 비대화형 진입 후 함께 처리되는 옵션 조합까지 금지하는 것으로 넓게 해석했다.
기존 구현은 제목·본문·태그처럼 유효한 비대화형 진입 조건이 하나라도 있으면 함께 지정한 수정 옵션을 같은 요청에서 처리한다.

## 영향

코드 결함은 없었지만 범위 경계의 의미를 다시 확인하는 검토가 한 차례 추가됐다.

## 대응

phase 범위 문구, `nonInteractive` 조건, 대화형 분기의 기존 경고와 편집기 호출을 근거로 동일 검토자에게 재평가를 요청했다.
검토자는 mention/link/parent가 직접 비대화형 진입 조건에 포함되지 않으므로 단독 호출 지원은 여전히 범위 밖으로 유지된다고 확인하고 최종 `PASS`를 판정했다.

## 검증

`hasParticipantChange`만 새 진입 조건으로 추가됐고 mention/link/parent 경고와 `$EDITOR` 경로가 유지되는지 코드와 검증 명령으로 확인했다.
독립 검토의 재평가 결과는 발견 없음과 `PASS`였다.

## 배운 점

비대화형 “진입 조건”과 진입 후 함께 적용되는 “조합 옵션”을 분리해 범위를 해석해야 한다.
검토 지적이 계획의 명시적 범위와 충돌하면 관련 코드 경로를 근거로 같은 검토자에게 재평가를 요청한다.

## 후속

현재 phase 문서가 “단독 호출 지원”이라고 범위를 명시하고 있어 별도 규칙으로 승격하지 않는다.
