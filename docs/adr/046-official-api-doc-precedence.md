## ADR-046: API 동작의 근거는 공식 문서이고 저장소 서술이 어긋나면 저장소를 고친다

- **status**: `accepted`

- **결정**: Dooray API 의 endpoint 존재 여부와 요청·응답 스키마와 동작 특이점은 공식 API 문서만을 근거로 삼는다.
  저장소의 ADR, `CLAUDE.md`, 스킬 문서, 코드 주석에 적힌 API 서술은 근거가 아니라 **그때의 확인 결과**로 읽는다.
  둘이 어긋나면 공식 문서를 따르고 저장소 서술을 고친다.

  구현된 endpoint 목록과 공식 목록의 대조를 스크립트로 두어 반복 실행한다.
  공식 목록은 스냅샷 파일로 저장소에 넣고, 갱신은 사람이 공식 문서를 다시 확인해 한다.

- **맥락**: Issue #154 의 계획을 세우는 동안 저장소 서술 셋이 사실과 다른 것을 찾았다.

  | 저장소 서술 | 어디에 | 공식 문서 |
  | --- | --- | --- |
  | 위키 API 가 page-only fetch 를 지원하지 않는다 | `CLAUDE.md`, `src/resolvers/wiki-page-input.ts` | `GET /wiki/v1/pages/{page-id}` 가 있다 |
  | 위키 페이지 이동 endpoint 가 없다 | `skills/dooray-cli/references/wiki.md`, ADR-032 의 참고 | `POST /wiki/v1/wikis/{wiki-id}/pages/{page-id}/move` 가 있다 |
  | 페이지 삭제는 미문서화 endpoint 다 | ADR-032 의 결정 | `DELETE /wiki/v1/wikis/{wiki-id}/pages/{page-id}` 가 문서에 있다 |

  첫 번째가 특히 비쌌다. 그 전제로 계획을 세워 「페이지 ID 만 알 때 project 를 찾는 절차」를 만들었는데,
  공식 endpoint 를 쓰면 그 절차 자체가 필요 없었다.
  잘못된 계획을 워커가 실행하기 시작한 뒤에 발견해 계획을 다시 썼다.

  `CLAUDE.md` 는 이미 새 endpoint 를 쓸 때 공식 문서를 브라우저로 확인하라고 정하고 있었다.
  규칙이 없어서 생긴 일이 아니다. 규칙이 **신규 endpoint 사용 시점**만 덮었고,
  이미 저장소에 적힌 서술을 사실로 받아들이는 경로를 덮지 않았다.

  서술이 오래되면 틀릴 수밖에 없다. 위 셋 중 둘은 당시에는 맞았을 수 있다.
  ADR-032 가 삭제를 미문서화로 판정한 것도 그때의 문서 상태였을 수 있다.
  그래서 서술을 탓하는 것이 아니라 근거의 우선순위를 정하는 것이 답이다.

  공식 문서는 React 앱이라 `WebFetch` 로 읽히지 않는다. 브라우저로 열어야 한다.
  그래서 CI 에서 매번 대조할 수 없고, 공식 목록을 스냅샷으로 두는 방식을 택한다.

- **대안 기각**:
  - 틀린 서술 셋만 고치고 끝낸다. 같은 종류가 또 쌓인다. 이번에 셋이 한꺼번에 나온 것이 그 근거다.
  - ADR 에 확인 날짜를 적어 오래된 것을 판별한다.
    날짜가 있어도 읽는 사람이 그 서술을 의심할 근거가 되지 않는다. 우선순위를 정하는 편이 직접적이다.
  - 공식 문서를 CI 에서 매번 대조한다.
    React 앱이라 브라우저가 필요하고, 공개 문서 페이지의 구조 변경에 CI 가 묶인다.
  - 저장소에서 API 서술을 모두 지우고 공식 문서 링크만 둔다.
    동작 특이점과 실측 결과는 공식 문서에 없다. ADR 이 그것을 담는 이유가 사라진다.

- **결과**:
  - 얻는 것: 저장소 서술과 공식 문서가 어긋났을 때 어느 쪽을 따를지 판단할 필요가 없다.
    스크립트가 구현되지 않은 공식 endpoint 를 목록으로 내주므로, 기능 요청이 들어왔을 때
    공식 API 에 이미 있는지를 먼저 확인할 수 있다.
  - 감당할 것: 공식 목록 스냅샷이 낡는다. 갱신을 사람이 해야 하고, 갱신하지 않으면 새 endpoint 를 놓친다.
    스냅샷과 공식 문서가 어긋난 상태는 스크립트가 알려주지 못한다.
    저장소의 API 서술을 읽을 때마다 그것이 근거가 아니라는 것을 기억해야 한다.

- **적용 범위**: 대조 대상은 `src/api/client.ts` 가 부르는 경로다.
  스크립트는 `scripts/` 에 두고 `node` 로 직접 돌린다. npm 의존성을 쓰지 않는다.
  검사가 `pnpm install` 앞에서 돌 수 있어야 하기 때문이다.

  실측으로 확인한 동작 특이점은 계속 ADR 이 담는다.
  공식 문서에 없거나 문서와 다르게 동작하는 것이 그 대상이고, 이 결정이 그것을 없애지 않는다.
