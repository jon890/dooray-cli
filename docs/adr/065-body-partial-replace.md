## ADR-065: 본문 부분 치환을 `post replace` 와 `wiki page replace` 로 둔다

**결정**: 업무와 위키 페이지의 본문에서 문자열 하나를 찾아 바꾸는 명령을 따로 둔다.

```
dooray post replace <대상> (--old <text> | --old-file <path>) (--new <text> | --new-file <path>) [--all] [--dry-run] [--no-confirm]
dooray wiki page replace <대상> (--old <text> | --old-file <path>) (--new <text> | --new-file <path>) [--all] [--dry-run] [--no-confirm]
```

| 명령 | 읽기 | 쓰기 | 보존하는 것 |
| --- | --- | --- | --- |
| `post replace` | `GET project/v1/projects/{id}/posts/{postId}` (`--id`·`--url` 이면 그 전에 `GET project/v1/posts/{postId}` 로 프로젝트를 해석한다) | `PUT project/v1/projects/{id}/posts/{postId}` | 제목·우선순위·마감·담당자·참조자·본문 형식. 태그는 `tagIds` 를 빼서 서버가 유지한다 |
| `wiki page replace` | `GET wiki/v1/wikis/{wikiId}/pages/{pageId}` | `PUT .../pages/{pageId}/content` | 제목(요청에 싣지 않는다)·본문 형식 |

old 는 공백과 줄바꿈까지 정확히 일치해야 한다. 0건이면 거부하고, 2건 이상이면 `--all` 이 있을 때만 모두 바꾼다.
파일과 stdin 으로 받은 old·new 는 UTF-8 BOM 과 끝 줄바꿈 하나를 떼고 비교한다. 인자로 받은 값은 그대로 쓴다.
치환으로 첨부 참조가 사라지면 두 명령 모두 확인을 받는다.

**맥락**: 본문을 바꾸는 수단이 `post edit --body`/`--body-file` 과 `wiki page edit --body`/`--body-file` 뿐이었다.
둘 다 본문 전체를 교체한다. 수천 줄짜리 런북에서 한두 줄을 고치려 해도 전문을 받아 고쳐 전부 다시 보내야 한다.
에이전트가 쓰면 본문 전체가 두 번 컨텍스트를 지나가고, 사람이 쓸 때도 번거롭다.

Dooray 를 다루는 다른 도구(MCP 서버)에는 `old_string` 을 찾아 `new_string` 으로 바꾸는 부분 치환이 있었고,
실사용에서 가장 많이 쓰인 기능 가운데 하나였다. 그 동작을 CLI 로 옮긴다.

**공식 API 문서의 `version` 서술**:

- 업무 `PUT /project/v1/projects/{project-id}/posts/{post-id}` 의 요청 본문에 `version` 이 있고,
  설명은 "null인경우 최신 버전으로 적용, version이 명시된 경우 수정하려는 버전과 다른경우 conflict 409 응답" 이다.
  같은 절의 HTTP 상태 코드 목록에는 200·401·403·404·500 만 있고 409 는 없다
- 업무 조회 응답 예시에는 `version` 이 없다. 문서 전체에서 업무 쪽 `version` 은 위 PUT 요청 본문 한 곳뿐이다
- 위키 `PUT /wiki/v1/wikis/{wiki-id}/pages/{page-id}/content` 의 요청 본문에는 `body` 만 있고 `version` 서술이 없다
- 그래서 `version` 을 싣지 않으면 문서상 최신 버전에 적용된다. 두 명령 모두 `version` 을 싣지 않으며, 이것이 문서대로의 사용이다

**실측으로 확인한 것** (2026-10-01, 개인 프로젝트의 테스트 업무 하나):

- **업무 PUT 에 `version` 을 실으면 문서의 409 가 아니라 400 으로 거절된다.** 값이 `0`·`1`·`999999` 어느 것이든
  `400 USER_INVALID_TASK_OVERWRITE` 였고 본문은 바뀌지 않았다. 조건부 갱신이라는 문서 서술과 동작은 맞지만 상태 코드가 다르다.
  맞는 값을 넣으면 통과할 것으로 보이나 **현재 값을 얻을 수단이 없다.** 상세 조회(`GET project/v1/posts/{postId}`,
  `GET project/v1/projects/{id}/posts/{postId}`)와 목록 조회 응답 어디에도 `version` 이 없었고, 문서의 조회 응답 예시에도 없다
- **HTTP 조건부 헤더는 무시된다.** `If-Match: "bogus"` 와 과거 시각의 `If-Unmodified-Since` 를 붙여도 `200` 으로 저장됐다.
  응답에 `ETag` 헤더도 없다
- **API 로 넣은 `<mark>` 는 왕복해도 그대로다.** `앞 <mark>형광펜 구간</mark> 뒤` 를 넣고 GET 하니 원문 그대로였고,
  그 구간을 `post replace` 로 바꾼 뒤에도 태그가 남았다
- **치환 후 나머지 필드가 그대로다.** `post replace` 전후로 상세 조회를 비교해 `body` 와 `updatedAt` 외에
  제목·우선순위·태그·담당자·참조자·마일스톤·워크플로우가 같았다. `mimeType` 도 `text/x-markdown` 그대로였다
- **CRLF 본문은 표본에서 나오지 않았다.** 개인 프로젝트의 업무 11건(모두 `text/x-markdown`)과 위키 페이지 6건의 본문을
  읽기 전용으로 훑어 `\r\n` 과 홀로 선 `\r` 이 모두 0건이었다. 표본이 작아 다른 프로젝트나 `text/html` 본문,
  웹 편집기 밖에서 들어온 본문에는 있을 수 있다고 보고 0건 안내만 둔다 (설계 결정 참고)
- **위키 인라인 이미지의 본문 참조는 `images[].id` 가 아니라 `images[].attachFileId` 를 쓴다.**
  본문 `![...](/wikis/<n>/files/<x>)` 의 `<x>` 가 `images[]` 의 `attachFileId` 와 같았고 `id` 와는 달랐다.
  `attachFileId` 는 **공식 문서 응답에 없는 필드다.** 문서의 `GET /wiki/v1/wikis/{wiki-id}/pages/{page-id}` 응답에서
  `files[]`·`images[]` 는 `id`·`name`·`size` 만 가진다. 실측으로만 확인한 값이라 첨부 참조 누락 확인에만 쓰고,
  응답에 없으면 `id` 만으로 확인한다.
  앞 숫자 `<n>` 은 그 위키의 wikiId 와 달랐다. 검출에는 앞 숫자를 쓰지 않는다.
  일반 첨부(`files[]`)가 본문에 어떤 형태로 들어가는지는 표본에 없어 확인하지 못했다
- **확인하지 못한 것**
  - 웹 편집기로 칠한 형광펜이 GET 에서 다른 표현으로 내려온다는 이야기가 있으나 재현해 보지 못했다.
    그렇다면 그 구간을 지나는 치환은 웹에서 보이는 것과 다른 본문을 저장한다
  - 위키 페이지 조회 응답에는 실측상 `version` 이 있다. 문서의 `PUT .../content` 요청 본문에 `version` 이 없어 싣지 않으며,
    실어 보는 시험도 하지 않았다. 시험용 위키 페이지가 없어 위키는 쓰기 실측을 하지 않았다

**설계 결정**:

- **`edit` 의 옵션이 아니라 별도 명령이다.** `post edit` 은 이미 제목·본문·본문 파일·멘션·업무 링크·참여자·태그·상위 업무·
  `--mime-type`·`--dry-run` 이 얽혀 있고, 옵션 조합으로 대화형과 비대화형이 갈린다.
  `--old`/`--new` 를 얹으면 `--body` 와의 충돌, 멘션·링크를 치환 전후 어디에 적용할지, `--dry-run` 출력이 본문 전체인지 구간인지가
  모두 새 규칙이 된다. 별도 명령은 "본문 일부만 바꾸고 나머지는 건드리지 않는다" 한 가지만 한다.
  사용자와 에이전트에게는 "본문 전체를 줄 때는 `edit`, 일부를 고칠 때는 `replace`" 라는 선택 기준이 생긴다
- **인자와 파일을 둘 다 받는다.** 짧은 한 줄은 `--old`/`--new` 가 편하고, 여러 줄이나 따옴표·백틱이 섞인 구간은
  셸 이스케이프를 피하려 파일이 낫다. `-` 는 `--body`/`--body-file` 과 같게 stdin 이다.
  stdin 은 한 번만 읽을 수 있으므로 old 와 new 가 함께 stdin 을 쓰면 읽기 전에 거부한다.
  인자·파일·stdin 을 읽는 규칙은 `--body`/`--body-file` 과 같은 헬퍼(`readTextInput`)를 쓰고, 아래 두 동작만 옵션으로 켠다
- **파일과 stdin 입력은 UTF-8 BOM 과 끝 줄바꿈 하나(`\n` 또는 `\r\n`)를 뗀다.** 에디터는 파일 끝에 줄바꿈을 붙이고
  `echo` 도 그렇다. 정확 일치라 그 줄바꿈 하나 때문에 0건이 되거나, 줄 끝까지 포함해 뜻보다 넓게 일치한다.
  BOM 은 본문에 들어갈 일이 없는 문자다. 끝 줄바꿈까지 일치시키려면 인자(`--old $'...\n'`)로 준다. 인자는 셸이 넘긴 그대로 쓴다.
  `--body-file` 은 본문 전체를 그대로 보내는 입력이라 이 처리를 하지 않는다. `--body -`·`--body-file -` 의 stdin 도 그대로다.
  `post create`·`wiki page create`·`mail send` 등의 본문이 조용히 달라지지 않도록 이 종전 동작을 테스트로 고정했다
- **없는 파일은 `EXIT_PARAM_ERROR` 로 알린다.** raw ENOENT 를 내면 종료 코드가 API 오류와 구분되지 않는다.
  `--body-file` 의 종전 동작은 바꾸지 않았다
- **옵션 조합 검사를 old·new 모두 끝낸 뒤에 읽는다.** old 를 stdin 으로 다 읽은 뒤 new 누락을 알리면 파이프로 보낸 입력이 버려진다
- **입력 검증을 설정 조회·API 호출보다 먼저 한다.** old 가 비었거나 old 와 new 가 같으면 바뀔 것이 없다.
  new 는 빈 문자열을 허용한다. 구간을 지우는 용도이고, 인자(`--new ""`)로 줄 때만 받는다(아래)
- **빈 파일 경로는 거부한다.** `readTextInput` 은 빈 경로를 "파일 없음" 으로 보고 빈 문자열을 돌려준다.
  `--new-file ""` 이 그대로 통과하면 빈 new 가 구간 삭제로 허용돼 old 구간이 지워진 채 저장된다.
  `--old-file ""` 도 "old 가 비어 있다" 로만 멈춰 원인이 경로라는 것을 말하지 않는다.
  그래서 `--old-file`·`--new-file` 이 빈 문자열(공백뿐인 값 포함)이면 stdin 을 읽기 전, 설정 조회 전에 경로가 비었다고 `EXIT_PARAM_ERROR` 로 멈춘다.
  인자로 준 빈 new(`--new ""`)는 삭제를 뜻하는 명시적인 값이라 계속 허용한다.
- **파일이나 stdin 으로 읽은 new 가 비면 거부하고, 구간 삭제는 인자 `--new ""` 로만 받는다.** 경로가 있어도 0바이트 파일,
  줄바꿈 하나만 든 파일(끝 줄바꿈을 떼면 빈 문자열이다), 빈 stdin 이면 new 가 `""` 로 읽혀 old 구간이 확인 없이 지워졌다.
  `생성명령 | dooray post replace ... --new -` 에서 앞 명령이 실패해 출력이 비는 경우가 여기에 걸린다.
  읽은 값만으로는 의도한 삭제와 실패한 입력을 가를 수 없으므로, 삭제 의도는 셸에서 직접 쓴 인자로만 받는다
- **유일성 규칙**: 일치가 0건이면 공백·줄바꿈까지 맞아야 한다고 안내하고, 2건 이상인데 `--all` 이 없으면 개수를 알려 거부한다.
  아무 곳이나 첫 번째를 바꾸면 사용자가 뜻한 곳이 아닐 수 있고, 긴 본문에서는 그것을 알아채기 어렵다.
  0건인데 본문에 `\r\n` 이 있고 old 에 `\r` 이 없으면 줄바꿈 형식이 다를 수 있다고 덧붙인다.
  일치 규칙을 줄바꿈 무시로 바꾸지 않은 것은 그러면 PUT 할 본문의 줄바꿈을 무엇으로 맞출지 새로 정해야 하고,
  위 실측에서 CRLF 본문을 만나지 못해 그 규칙을 검증할 수 없었기 때문이다.
  같은 방식으로, 0건이지만 본문과 old 를 모두 NFC 로 정규화하면 일치하는 경우 유니코드 정규화 형식(NFC/NFD)이 다르다고 덧붙인다.
  macOS 파일 이름 등에서 복사한 한글은 NFD 라 눈으로는 같아도 정확 일치가 0건이 된다.
  일치 규칙을 정규화 비교로 바꾸지 않은 것도 같은 이유다. 바꾸면 PUT 할 본문의 정규화 형식을 새로 정해야 한다.
  두 안내는 함께 나올 수 있다.
  일치 개수는 겹치는 위치까지 센다(`aaa` 에서 `aa` 는 2군데). 겹침을 빼면 한 군데로 보여 모호함을 놓친다.
  `--all` 은 앞에서부터 겹치지 않는 구간을 바꾸므로, 겹침이 있으면 거부 메시지의 개수보다 적게 바뀔 수 있다
- **치환에 `String.prototype.replace` 를 쓰지 않는다.** 치환 문자열의 `$&`·`$1` 을 패턴으로 해석해, new 에 `$` 가 들어 있으면 결과가 달라진다
- **`--dry-run` 은 바뀌는 줄만 보이고, 긴 줄은 바뀐 곳 주변만 남긴다.** 실제로 바뀐 글자를 품은 줄을 원본(`-`)과 결과(`+`)로 diff 처럼 낸다.
  old 와 new 의 공통 앞뒤는 바뀌지 않으므로 빼고 줄을 찾는다. 일치 구간을 그대로 쓰면 old·new 가 함께 `\n` 으로 끝날 때
  구간 끝이 다음 줄 머리에 걸려 바뀌지 않는 다음 줄까지 나온다(`\n` 으로 함께 시작하면 앞 줄). 바뀐 글자에 줄바꿈이 들어 있으면
  그 줄바꿈으로 합쳐지거나 갈라진 다음 줄까지 낸다. 줄 번호는 바뀐 글자가 시작하는 줄이다.
  같은 줄에 걸친 위치는 한 구간으로 합친다. 본문 전체를 내면 긴 본문의 일부만 보내려던 이 명령의 목적이 무색해진다.
  줄바꿈 없는 긴 본문에서는 그 "줄" 이 본문 전체라 미리보기가 본문을 두 번 낸다(5,010자 한 줄이면 출력이 10,042자).
  그래서 표 출력에서만 줄인다. 구간마다 원본과 결과의 공통 접두·접미를 구하고(접미는 접두와 겹치지 않게),
  공통 접두 가운데 첫 변경이 있는 줄의 앞머리가 160자(앞뒤 문맥 80자의 두 배)를 넘으면 끝 80자만 남기고 앞을 `...` 로,
  공통 접미 가운데 마지막 변경이 있는 줄의 뒷부분이 160자를 넘으면 앞 80자만 남기고 뒤를 `...` 로 줄인다.
  공통 부분이라 원본과 결과에 같은 잘림을 적용한다. 줄을 넘어 자르지 않으므로 줄 수와 `N번째 줄` 표기는 그대로이고,
  한 줄에 여러 군데가 바뀌면 변경 사이는 공통 접두·접미 바깥이라 자르지 않는다.
  잘림은 제어문자 치환 전에 원문 기준으로 하고, 경계가 서로게이트 쌍 가운데에 오면 한 칸 옮긴다.
  생략 표기는 CR 표기와 같은 이유로 유니코드 말줄임표가 아니라 ASCII `...` 다.
  **잘린 줄은 미리보기를 복사해 다음 `--old` 로 그대로 쓸 수 없다.** 잘린 자리에 원문 대신 `...` 가 있기 때문이다.
  짧은 줄은 줄이지 않으므로 종전처럼 복사해 쓸 수 있고, 긴 줄의 old 는 `post get --json`·`wiki page get --json` 의 본문에서 잘라 온다.
  `--json` 의 `hunks` 는 줄이지 않고 줄 전체를 담는다.
  `--json` 과 함께 주면 `{ dryRun, replaced, mimeType, hunks: [{ line, before, after }] }` 로, `--quiet` 이면 바뀔 군데 수 한 줄로 낸다.
  서버 본문 조각을 터미널에 낼 때는 제어문자를 치환하되 **탭은 그대로 두고 CR 은 `<CR>` 로 보인다.** 유니코드 제어 그림 문자(U+240D)는 터미널 폰트에 따라 깨질 수 있어 ASCII 로 둔다.
  사용자가 미리보기를 복사해 다음 `--old` 를 만들기 때문에, 탭을 `?` 로 바꾸면 복사본이 0건이 된다. 탭은 커서를 앞으로만 옮겨 터미널에 안전하다.
  CR 은 커서를 줄 머리로 돌려 앞 글자를 덮어쓰므로 그대로 둘 수 없고, `?` 는 원문의 `?` 와, 글자 `\r` 은 코드 예시에 적힌 `\r` 과 헷갈린다.
  공용 `sanitizeMultilineForTerminal` 의 기본 동작(탭과 CR 을 `?` 로, CRLF 를 LF 로)은 그대로 두고 옵션으로 켠다
- **본문 형식은 `resolveBodyMimeType` 으로 기존 값을 보존한다** (ADR-053). `--mime-type` 은 두지 않는다.
  일부만 바꾸는 명령이 본문 전체의 형식을 바꾸면 나머지 부분이 깨진다
- **업무는 `post edit` 의 첨부 누락 경고를 그대로 쓴다.** 치환으로 `/files/<id>` 참조가 사라지면 `checkAndGuardDropped` 가
  경고하고 확인을 받는다. `--no-confirm` 으로 넘긴다. `--dry-run` 에서는 확인하지 않는다 (`post edit` 과 같다)
- **위키에도 같은 첨부 경고를 넣었다.** 위키 본문의 참조는 `/wikis/<n>/files/<id>` 형태라 `/files/<id>` 만 찾던 검출식을
  앞 segment 를 선택으로 받게 넓혔다. 업무 본문에는 이 형태가 나오지 않아 `post edit`·`post replace` 의 동작은 같다.
  비교할 첨부 목록은 `files[]` 와 `images[]` 의 `id` 에 `attachFileId` 를 더한 것이다 (실측 항목).
  `attachFileId` 는 공식 문서 응답에 없는 필드라 없으면 `id` 만으로 비교한다. 업무 쪽과 같게 `--dry-run` 에서는 확인하지 않는다.
  `wiki page edit` 에는 아직 넣지 않았다. `replace` 는 일부만 고친다고 여겨 확인 없이 쓰기 쉬워 먼저 넣었고, `edit` 은 후속으로 다룬다
- **왕복의 한계를 그대로 둔다.** 부분 치환도 내부적으로는 현재 본문을 읽고 바꿔 전체를 다시 보낸다.
  읽고 보내는 사이에 누군가 본문을 고치면 그 수정을 덮어쓴다. 업무 PUT 의 `version` 은 싣지 않으면 문서상 최신 버전에 적용되므로
  싣지 않는다. 실으면 조건부 갱신이 되지만 현재 값을 돌려주는 조회 응답이 문서에도 실측에도 없어 쓸 수 없다.
  위키 `PUT .../content` 는 문서상 `version` 을 받지 않는다. HTTP 조건부 헤더는 서버가 보지 않는다.
  덮어쓸 수 있는 구간은 GET 과 PUT 사이이고, 첨부 누락 확인을 기다리는 동안 길어진다. 같은 업무를 여럿이 동시에 편집하는 상황이면 웹에서 고치는 편이 낫다고 사용자 문서에 적는다.
  보내기 직전에 한 번 더 GET 해 비교하는 방식은 창을 줄일 뿐 없애지 못하고 호출을 늘려 넣지 않았다

**대안 기각**:

- **`post edit --old/--new`** — 위 설계 결정의 첫 항목. `edit` 의 옵션 조합 규칙이 한 번 더 복잡해진다
- **정규식 치환** — 에이전트와 사람 모두 본문의 특수문자를 이스케이프해야 해 정확 일치보다 실수가 잦다.
  필요한 경우는 `--all` 과 여러 번의 호출로 대신한다
- **2건 이상이면 첫 번째만 바꾼다** — 유일성 규칙 항목. 뜻하지 않은 곳이 바뀌어도 알아채기 어렵다
- **`--dry-run` 에 본문 전체를 낸다** — 긴 본문에서 바뀐 곳을 찾기 어렵고 전송량을 줄이려던 목적과 어긋난다.
  전체가 필요하면 치환 후 `post get --json` 으로 본다
- **hunk 자체를 잘라 `--json` 도 줄인다** — raw 에 가까운 구조화 출력을 사람용 표시 규칙에 묶게 된다.
  `--json` 을 받는 쪽이 잘린 조각을 old 로 다시 쓰면 0건이 된다
- **`version` 으로 조건부 갱신** — 업무는 공식 문서상 PUT 요청 본문에만 `version` 이 있고 조회 응답에는 없어 현재 값을 얻을 수단이 없다.
  알 수 없는 값을 넣으면 실측에서 모든 요청이 `400 USER_INVALID_TASK_OVERWRITE` 로 거절됐다(문서는 409 라고 적는다).
  위키 `PUT .../content` 는 문서상 `version` 을 받지 않는다. 문서의 조회 응답에 `version` 이 생기면 다시 검토한다
