## ADR-040: 웹 메일 URL 의 mail id 를 IMAP UID 로 매핑하지 않는다

**결정**: `dooray mail get` 과 `dooray mail reply` 는 IMAP UID 만 받는다.
웹 메일 주소와 그 주소에 들어 있는 19자리 mail id 는 형태로 알아보고, 조회를 시도하지 않은 채 안내와 함께 거절한다.

**맥락**: 사람이 메일을 공유할 때 실제로 건네는 값은 웹 주소다.

```
https://<tenant>.dooray.com/mail/systems/inbox/<mail-id>
```

Dooray 는 메일 조회 REST API 를 제공하지 않아 이 기능은 IMAP 위에 있다 (ADR-012).
그래서 주소의 mail id 를 IMAP UID 로 바꿀 수단이 있는지 실제 사서함으로 확인했고, 세 가지가 모두 막혔다.

- IMAP 서버가 `HEADER x-dooray-mail-id <값>` 검색에 빈 결과를 준다. 같은 형식의 `message-id` 검색은 정상 동작하므로 서버가 이 헤더를 색인하지 않는 것이다.
- `X-Dooray-Mail-Id` 헤더 자체가 일부 메일에만 붙는다. 받은 메일함 최근 300통 중 50통만 갖고 있었다.
- 공유받은 주소의 id 는 사서함 전 폴더를 훑어도 어느 메일의 헤더 값과도 일치하지 않는다. 헤더에 박히는 값은 보낸 사람 쪽 사본의 id 이고, 주소의 id 는 받는 사람 쪽 사본의 id 이기 때문으로 보인다.

**대안 기각**:

- 헤더를 클라이언트가 직접 훑어 매핑 — 위 세 번째 이유로 애초에 일치하지 않는다. 설령 일치하더라도 헤더 수신에 200통 약 7초, 1000통 약 67초가 걸려 단건 조회에 쓸 수 없다.
- 입력을 UID 로 간주하고 그대로 서버에 넘기기 — 이 동작이 지금의 결함이다. 19자리는 JavaScript 안전 정수 범위를 넘어 `Number()` 를 거치면 값이 바뀌고, 사용자는 입력하지 않은 숫자가 적힌 오류를 받는다.

**대신 하는 것**: 32비트 경계로 두 체계를 가른다.
IMAP UID 는 32비트 부호 없는 정수라 최대 4294967295 이므로, 그 범위를 넘는 숫자는 UID 일 수 없다.
분류를 조회보다 앞에 두어 안전 정수 범위 밖 값이 `Number()` 에 도달하지 않게 하고, 오류 메시지에는 입력 문자열을 그대로 싣는다.
경계 비교는 `BigInt` 로 한다. 이 비교를 `Number()` 로 하면 판정하려는 정밀도를 판정하는 자리에서 다시 잃는다.

**되돌리는 조건**: Dooray 가 메일 조회 API 를 공개하거나, IMAP 서버가 받는 사람 쪽 mail id 를 헤더나 검색으로 노출하면 이 결정을 다시 본다.
