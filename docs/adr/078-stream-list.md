## ADR-078: 활동 피드를 `stream list` 로 두고 `--since` 는 응답 커서로 멈춘다

**결정**: `GET /common/v1/streams` 를 `dooray stream list` 로 감싼다.
옵션은 `--size`(기본 20, 최대 200), `--before <cursor>`, `--since <YYYY-MM-DD|ISO8601|prev-<N>d>`, `--unread`, `--all` 이다.

- 기본은 한 페이지만 받고, 다음 커서를 stderr 에 `다음 페이지: --before <cursor>` 로 알린다.
- `--all` 은 빈 배열이 올 때까지 페이지를 넘긴다.
- `--since` 는 응답 `cursor` 가 그 시각보다 60초 넘게 앞서면 멈춘다. 원소는 자기 시각이 그보다 앞서면 뺀다.
  시각 필드가 없는 원소는 그 페이지 커서가 since 이후일 때만 남긴다.
- `--all`·`--since` 에서 `--size` 를 주지 않으면 페이지마다 200건을 받는다. 페이지 상한은 1000이다.
- `--unread` 는 `read=false` 로 보낸다.
- `--json` 은 API `result` 원소를 바꾸지 않고 모은 배열로 낸다. 표는 시각, 타입, 작성자, 제목·내용 열이다.
- HTTP 429 는 ky 재시도 3회 뒤에도 남으면 종료 코드 6(`EXIT_RATE_LIMITED`)으로 끝낸다.
  이 분기는 `src/api/public/http.ts`·`src/api/web/http.ts` 의 공통 오류 변환과, status 를 직접 보는 첨부 다운로드·업로드 경로에 함께 두어 모든 명령에 적용된다.

**맥락**: fos-skills 의 보드 알림함이 두레이 알림을 5분마다 읽는다.
토큰을 한곳에 두려고 그 adapter 가 이 CLI 를 부르기로 했고, 명령 계약은 그쪽이 정했다(2026-11-02).
429 를 다른 오류와 나눠야 부르는 쪽이 기다렸다 다시 부를지 판단할 수 있다.

**공식 문서가 정한 것** (Common > Streams 절, 2026-11-02 확인):

- 요청 시각 기준 최근 2주만, 항상 최신 활동순으로 준다.
- `size` 기본 20, 최댓값 200. `before` 는 직전 응답의 `cursor`(timestamp). `read` 는 읽음 여부 필터다.
- 응답 건수가 `size` 보다 적어도 마지막 페이지가 아니다. 빈 배열이 올 때까지 이어 불러야 한다.
- 원소는 `{ "type": "<타입>", "<타입>": {...} }` 이고 타입은 project, mail, schedule, event, post, page, pageComment, fileEvent 다.
- 문서 예시의 `cursor` 는 `"1781768002000000000"` 처럼 19자리 문자열이다.

**실측으로 확인한 것** (2026-11-02, 실제 계정, 읽기만):

- 2주 치 전체가 5113건이었다. `size=200` 한 페이지에 189건이 왔다. 200건씩 넘기면 30페이지 안팎이다.
- 한 페이지 189건의 type 분포는 mail 153, event 31, post 2, page 1, pageComment 1, schedule 1 이었다.
- `cursor` 는 나노초 timestamp 이고, 그 페이지 마지막 원소의 시각과 수십 초 안에서 맞았다.
- 문서 예시에 없는 `event.createdAt`·`event.updatedAt` 이 실제로 온다. `pageComment` 에는 `wikiId` 가 더 온다.
- 한 페이지 189건 중 6건은 `createdAt` 과 `updatedAt` 이 달랐다. 활동 시각은 시각 필드 가운데 가장 늦은 값으로 읽는다.
- `schedule` 에는 활동 시각 필드가 없다. `startedAt` 은 일정 시각이라 활동 시각으로 쓰지 않는다.
- 원소 시각(`createdAt`·`sentAt` 등)은 최신순에서 최대 29초 어긋났다(1184건 중 29곳).
  원소 시각이 since 보다 앞선 첫 원소에서 멈추면 뒤에 오는 since 이후 원소를 놓칠 수 있어, 멈춤은 커서로 판단한다.
  커서가 since 를 막 지난 페이지 다음에도 since 이후 원소가 올 수 있어, 어긋남보다 큰 60초 여유를 둔다.
- `--unread` 로 받은 200건 중 `read: true` 인 원소는 없었다.

**검토한 대안**:

- 429 종료 코드를 `stream list` 에만 두는 안: 다른 명령의 429 는 종료 코드 1 로 남는다.
  오류 변환이 공통 함수 하나라 명령별 분기가 필요해지고, 429 를 구분하는 이점을 다른 명령이 얻지 못해 택하지 않았다.
- `--since` 를 원소 시각만으로 멈추는 안: 위 실측의 시각 어긋남 때문에 택하지 않았다.

**결과**: 종료 코드 6 은 모든 명령에서 「호출 한도 초과」 를 뜻한다. 0 이 아닌지만 보는 스크립트는 영향이 없다.
