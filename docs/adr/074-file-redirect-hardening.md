## ADR-074: 첨부 파일 redirect 는 같은 도메인의 https 주소에만 인증 헤더를 싣고, 다운로드는 첫 응답까지만 시간을 잰다

- **status**: `accepted`

- **결정**: 업무·위키 첨부의 다운로드와 업로드가 307 을 따라갈 때 `src/api/file-redirect.ts` 의 helper 를 함께 쓴다 (Issue #232).
  - **`location` 은 `https` 이고, API 주소가 `api.` 로 시작하면 그 `api` 를 뺀 도메인과 하위 도메인일 때만 따라간다.**
    `https://api.dooray.com` 이면 `file-api.dooray.com` 은 되고 `dooray.com.example.net` 이나 `http://` 주소는 안 된다.
    API 주소가 IP 주소이거나 `api.` 로 시작하지 않으면 그 호스트 자신만 믿는다.
    어긋나면 인증 헤더를 보내지 않고 `EXIT_API_ERROR` 로 멈춘다. 오류에는 그 주소의 origin 만 싣는다. 경로와 쿼리에 서명 같은 값이 있을 수 있다.
  - **파일 서버가 다시 redirect 하면 따라가지 않고 멈춘다.** 파일 서버 요청은 `redirect: "manual"` 로 보낸다.
  - **다운로드의 파일 서버 요청은 응답 헤더가 30초 안에 오지 않으면 끊는다.** 헤더를 받은 뒤에는 시간을 재지 않는다.
    업로드에는 걸지 않는다. 업로드는 본문을 다 보낸 뒤에야 헤더가 와서, 이 제한이 곧 전송 시간 제한이 된다.
  - **다운로드는 api 서버가 307 이 아닌 status 를 주면 파일 서버를 부르지 않고 실패한다.** 위키 쪽만 하던 확인을 업무 쪽에도 둔다.
  - **첨부 다운로드·업로드 경로에 넣는 id 는 `encodeURIComponent` 로 감싼다.** 첨부 목록과 삭제를 포함한 `client.ts` 의 다른 경로는
    이번에 바꾸지 않았고 [ADR-075](075-api-path-encoding.md) 가 모든 경로로 넓혔다. 이 경로의 `enc` 상수는 `apiPath` 로 바뀌었다.

- **맥락**: ADR-015 는 307 을 수동으로 따라가며 `location` 에 같은 인증 헤더를 다시 싣기로 했다.
  그 뒤 업무 다운로드·업로드, 위키 다운로드·업로드가 각자 같은 흐름을 따로 구현했다. `location` 을 확인하는 곳은 없었고,
  파일 서버 요청은 ky 인스턴스를 거치지 않는 bare `fetch` 라 시간 제한이 없었다. 307 확인도 위키 쪽에만 있었다.
  #231 리뷰에서 이 지적이 나왔고, 저장소 공통이라 그 PR 이 아니라 이 결정으로 다룬다.

- **실측** (2026-10-23): API 주소가 `https://api.dooray.com` 인 테넌트에서 업무 첨부 다운로드 경로가 `307` 과
  `location: https://file-api.dooray.com/...` 를 줬다. status 와 `location` 의 scheme·host 만 확인했다.

- **아직 확인하지 못한 것**:
  - 공공·공공 업무망·금융 클라우드(`api.gov-dooray.com`, `api.gov-dooray.co.kr`, `api.dooray.co.kr`)의 `location` 이
    같은 모양(`file-api.<도메인>`)인지. 규칙은 같은 모양을 가정한다. 다르면 인증 헤더를 보내지 않고 멈추는 쪽으로 틀린다.
  - 위키 첨부와 업로드의 `location` 호스트. 업무 다운로드와 같은 파일 서버라고 가정한다.

- **설계 결정**:
  - **허용 범위를 API 주소에서 끌어낸다.** 호스트 목록을 고정하면 클라우드가 늘 때마다 고쳐야 하고, 설정의 API 주소와 어긋날 수 있다.
    `api` 하나만 빼므로 `api.dooray.com` 설정이 `gov-dooray.com` 을 믿는 일은 없다.
    `api.` 로 시작하지 않는 주소에서 앞 이름을 무조건 떼면 `example.co.kr` 설정이 `co.kr` 전체를 믿게 되고,
    IP 주소에서 떼면 `10.168.0.5` 설정이 `99.168.0.5` 를 믿게 된다. 그래서 이 둘은 호스트 자신만 믿는다.
  - **`file-api.` 로 좁히지 않고 도메인 전체를 믿는다.** 실측한 것은 `file-api.dooray.com` 하나뿐이고 다른 클라우드의 파일 서버 이름은 모른다.
    좁히면 확인하지 못한 클라우드에서 첨부가 모두 막힐 수 있다. 같은 회사가 운영하는 도메인 안이라 위험이 작다고 판단했다.
  - **다운로드는 첫 응답까지만 잰다.** 전체 시간을 끊으면 큰 파일이 중간에 잘린다. 막으려는 것은 서버가 답하지 않아 명령이 끝나지 않는 경우다.
  - **id 인코딩을 첨부 경로로 한정한다.** `client.ts` 의 다른 경로에도 인코딩이 없지만, 이번 범위는 인증 헤더가 다른 경로로 새는 첨부 흐름이다.
    나머지는 이슈로 따로 다뤘고 ADR-075 가 맡았다.

- **대안 기각**:
  - **`location` 을 확인하지 않고 그대로 따라가기** — 지금까지의 동작이다. 서버 응답 하나로 토큰이 다른 호스트로 갈 수 있다.
  - **파일 서버 요청을 ky 인스턴스로 보내기** — ky 의 `prefix` 와 재시도, 토큰 버킷은 api 서버용이고, ADR-015 가 적었듯 업로드는 ky 와 `redirect: "manual"` 조합이 맞지 않는다.

- **유지**: 메신저 첨부 다운로드(ADR-072, #231)도 같은 helper 를 쓴다. 파일 서버 404 의 안내 문구는 호출자가 helper 에 넘긴다.
