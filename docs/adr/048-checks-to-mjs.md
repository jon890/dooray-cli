## ADR-048: 문서 검사 스크립트를 셸에서 `.mjs` 로 옮긴다

- **status**: `accepted`

- **결정**: `scripts/check-pii.sh` 와 `scripts/check-public-refs.sh` 를
  `scripts/check-pii.mjs` 와 `scripts/check-public-refs.mjs` 로 옮긴다.
  `node:` 빌트인만 쓰고 npm 의존성을 쓰지 않는다.
  검사 규칙을 export 해 vitest 로 단위 테스트한다.
  CI 의 실행 위치는 바꾸지 않는다.

- **맥락**: 두 스크립트는 공개 저장소에 사내 식별자와 내부 추적 번호가 새는 것을 막는다.
  CI 가 같은 스크립트를 돌리므로 통과하지 않으면 PR 이 막힌다.

  셸로 남을 때의 문제가 실제로 났다.
  `scripts/check-pii.sh` 의 첫 주석이 그것을 적고 있다.
  「shebang 으로 bash 를 고정한다. zsh 는 배열을 다르게 확장해 검사 대상이 조용히 첫 원소 하나로 줄어든 적이 있다」다.
  `SCAN` 이 배열이라 확장 규칙이 다른 셸에서 검사 범위가 아홉 개에서 하나로 줄었다.
  검사는 그래도 통과하므로 범위가 줄었다는 것이 드러나지 않는다.

  같은 문제가 이 저장소 밖에서도 재현된다. zsh 에서 공백으로 이은 문자열을 변수에 담아
  명령 인자로 넘기면 단어로 나뉘지 않고 한 인자가 된다.
  브랜치 12개를 지우려던 명령이 그 이름들을 이어 붙인 한 이름으로 해석된 적이 있다.

  검사 규칙에 단위 테스트를 붙일 수 없는 것도 비용이다.
  `OK_DOMAINS` 는 호스트 경계에 앵커해야 `dooray.com` 이 `evil-dooray.com` 안에서 매치되지 않는다.
  그 주석이 스크립트에 적혀 있지만 그 성질을 검증하는 테스트가 없다.
  화이트리스트가 늘 때마다 사람이 다시 읽어야 한다.

- **왜 Python 이 아니라 `.mjs` 인가**: CI 가 Node 만 설치한다.
  `.github/workflows/ci.yml` 이 `pnpm/action-setup` 과 `actions/setup-node` 만 쓰고 `setup-python` 이 없다.
  Python 을 넣으면 TypeScript 프로젝트에 선언되지 않은 런타임이 하나 늘어난다.
  이 저장소에 있던 Python 시제품 둘이 `dotenv` 를 요구하면서 저장소 의존성에는 없는 상태로 방치된 적이 있다.

  검사 스텝이 `pnpm install` 앞에서 돈다. `ci.yml` 의 순서가 그렇다.
  그래서 npm 의존성을 쓸 수 없고 `tsx` 로 `.ts` 를 돌리는 길도 막힌다.
  `node:` 빌트인만 쓰는 `.mjs` 는 두 제약을 모두 지나간다.

  `scripts/verify-package.mjs` 가 같은 방식의 선례다. `node:fs` 와 `node:path` 만 쓰고 `node` 가 직접 실행한다.

- **왜 CI 의 실행 위치를 바꾸지 않는가**: `actions/setup-node` 가 검사 스텝보다 앞에 있어 Node 가 이미 있다.
  검사가 `pnpm install` 앞에 있는 이유는 공개 저장소에서 식별자 노출이 한 번 새면 되돌리기 어렵다는 것이고,
  그 이유는 런타임과 무관하다.
  다만 그 자리의 주석이 「문서 검사는 Node 가 필요 없고」라고 적고 있어 사실과 달라진다. 그 문장을 고친다.

- **대안 기각**:
  - 셸을 유지하고 `SCAN` 을 배열이 아닌 형태로 바꾼다. 이번 함정 하나는 사라지지만
    인용과 종료 코드와 정규식 방언 문제는 남고 단위 테스트도 여전히 붙지 않는다.
  - TypeScript 로 옮긴다. `tsx` 가 devDependency 에 없고, 있어도 `pnpm install` 앞에서는 쓸 수 없다.
    빌드해서 쓰는 것도 같은 이유로 막힌다.
  - 검사를 `pnpm install` 뒤로 옮기고 TypeScript 로 쓴다.
    의존성 설치가 실패하면 식별자 검사가 아예 돌지 않는다. 가장 중요한 검사를 가장 나중에 두는 것이다.
  - Python 으로 옮긴다. CI 에 런타임이 하나 늘고, 우분투 러너에 있는 `python3` 에 기대는 것은 선언되지 않은 의존이다.

- **결과**:
  - 얻는 것: 셸의 배열 확장과 인용 규칙에 검사 범위가 좌우되지 않는다.
    검사 규칙을 함수로 export 해 vitest 로 검증할 수 있다.
    호스트 경계 앵커처럼 주석으로만 남아 있던 성질에 테스트가 붙는다.
    화이트리스트를 추가할 때 실수를 테스트가 잡는다.
  - 감당할 것: 두 파일의 호출 지점이 저장소 안 7개 파일 14줄이다. 전부 함께 고쳐야 한다.
    CI 의 검사 스텝이 Node 에 의존하게 되므로, `setup-node` 가 그 앞에 있어야 한다는 제약이 새로 생긴다.
    그 순서를 바꾸면 검사가 실행되지 않는다.

- **적용 범위**: 두 스크립트만 대상이다. `scripts/verify-package.mjs` 는 이미 `.mjs` 다.
  셸 스크립트는 이 둘 외에 없다.

  화이트리스트와 검사 범위 목록의 소유자는 바뀌지 않는다.
  `SCAN` 과 `OK_DOMAINS` 와 `OK_IDS` 와 `OK_PROJECTS` 를 새 파일이 그대로 갖는다.
  `CLAUDE.md` 는 그 목록을 그 파일이 소유한다고 계속 가리킨다.
