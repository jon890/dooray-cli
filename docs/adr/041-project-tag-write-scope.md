## ADR-041: 프로젝트 태그 쓰기를 공식 문서 지원 범위로 한정한다

**결정**: `project tags` 하위에 태그 생성(`create`)과 태그 그룹 속성 변경(`group`)만 둔다.
태그 이름·색상 수정과 태그 삭제는 구현하지 않는다. 공식 API 문서에 해당 경로가 없다.

생성과 그룹 속성 변경은 `src/services/tag.ts` 의 쓰기 함수를 거치고, 그 함수가 태그 캐시를 지운다.
캐시 무효화를 어느 계열이 맡는지는 [ADR-042](042-cache-invalidation-on-mutation.md) 가 소유한다.

**맥락**: 태그를 업무에 붙이는 일은 `post edit --tag` 로 되지만, 붙일 태그를 만드는 단계만
웹 설정 화면에 남아 있었다 (Issue #146). 태그가 필수인 프로젝트에서 태그 체계를 새로 잡으려면
CLI 밖으로 나가야 한다.

공식 API 문서에서 확인한 태그 관련 경로는 넷이다.

| 경로 | 지원 |
| --- | --- |
| `POST /project/v1/projects/{id}/tags` | 생성. `name` 은 `"그룹명:태그명"` 이고 그룹명은 선택 |
| `GET /project/v1/projects/{id}/tags` | 목록. 이미 구현되어 있다 |
| `GET /project/v1/projects/{id}/tags/{tag-id}` | 단건 조회 |
| `PUT /project/v1/projects/{id}/tag-groups/{id}` | 그룹의 `mandatory` 와 `selectOne` 변경 |

태그 수정과 삭제, 그룹 이름 변경은 문서에 없다.

**미확인**: 문서에 없는 `PUT .../tags/{id}` 와 `DELETE .../tags/{id}` 가 실제로 동작하는지는
확인하지 않았다. 태그 삭제가 지원되지 않으면 탐색용으로 만든 태그가 상용 프로젝트에 남아
웹 UI 로 지워야 하므로, 확인 비용이 얻는 것보다 크다고 판단했다.

**그룹을 태그 목록에서 파생한다**: 그룹 목록을 주는 경로가 없어, 그룹 정보는 태그 목록 응답의
`tagGroup` 필드에서 모은다. 그래서 태그가 하나도 없는 그룹은 CLI 가 찾을 수 없고,
`group` 명령은 태그가 최소 하나 있는 그룹만 대상으로 삼는다.

**그룹 속성은 병합해서 보낸다**: `PUT tag-groups` 는 `mandatory` 와 `selectOne` 을 함께 받는다.
한쪽만 바꿀 때 다른 쪽이 초기화되지 않도록 현재 값을 읽어 병합한 전체 body 를 보낸다.
`post edit` 이 제목·본문을 다시 실어 보내는 것과 같은 이유다.

**단건 조회를 넣지 않는다**: `GET .../tags/{tag-id}` 는 문서상 지원되지만 명령으로 만들지 않는다.
목록이 이미 같은 필드를 모두 주고, 태그 수가 프로젝트당 수십 개 수준이라 단건 경로가 얻는 것이 없다.

**대안 기각**:

- 문서에 없는 수정·삭제를 실측으로 확인해 함께 구현 — 실패 시 상용 프로젝트에 태그가 남는다.
  이슈의 주 목적인 "새 태그 그룹을 만드는 단절"은 생성만으로 해소되므로 확인을 미뤘다.
- `--name` 을 반복 받아 여러 태그를 한 번에 생성 — API 가 단건만 받아 CLI 가 순차 호출하게 된다.
  중간 실패 시 어디까지 만들어졌는지를 별도로 알려야 해서, 명령 하나가 호출 하나에 대응하는 편이 단순하다.
- `--color` 를 필수 인자로 — 자동화 스크립트가 매번 색을 골라야 한다. 무채색 기본값을 둔다.

**적용 범위**:

- `POST` body 의 `color` 는 `#` 없는 6자리 hex 다. 사용자가 `#` 을 붙여 넣으면 벗겨서 보낸다.
  생략 시 기본값은 `e0e0e0` 이다. 문서 예시의 `ffffff` 는 흰 배경과 구분되지 않아 쓰지 않는다.
- `project tags` 를 그룹 명령으로 바꾸면서 기존 `project tags <project>` 호출을 그대로 남긴다.
  이미 공개 문서에 실려 있어 스크립트가 쓰고 있다.
