## ADR-061: 메신저 대화방 읽기를 `messenger logs` 로 두고 최근 N건까지만 지원한다

**결정**: `GET /messenger/v1/channels/{channel-id}/logs` 를 `dooray messenger logs <channel>` 로 감싼다.
`-n` 으로 개수를 받고 상한은 1000 이다. 날짜 필터와 페이징은 API 에 수단이 없어 두지 않는다.

**맥락**: messenger 명령이 `send` 와 `channel-send` 와 `thread-send` 뿐이라 쓰기만 가능했다.
대화방에 쌓인 내용을 읽어 요약하거나 옮겨 적는 일은 CLI 밖에서 따로 스크립트를 짜야 했다.

대화방 목록 조회(`GET /messenger/v1/channels`)와 이름 해석(`resolveMessengerChannel`)은
`channel-send` 를 위해 이미 있었으므로, 추가한 것은 로그 조회 한 경로다.

**실측으로 확인한 것**:

응답 형태와 파라미터 동작은 실제 API 호출로 확인했다.

응답은 `{ header, result, hasMore }` 이고 `totalCount` 는 없다.
로그 항목은 `id` `seq` `sender` `sentAt` `text` `type` `flags` 를 가진다.

- **`size` 는 동작하고 상한은 1000 이다.** `size=3` 은 3건, `size=100` 은 100건을 준다.
  `size=5000` 을 줘도 1000건에서 멈춘다.
- **페이징 수단이 없다.** `page=1` 과 `page=2` 가 같은 구간을 돌려준다.
  커서로 쓸 만한 이름 여섯 가지(`beforeSeq` `before` `seq` `fromSeq` `lastSeq` `until`)를 시험했고
  전부 무시돼 같은 결과가 왔다. 날짜 파라미터도 마찬가지다.
- **`hasMore` 는 1000건을 받아도 `true` 다.** 더 있다는 신호는 주지만 가져갈 방법이 없다.
- `seq` 내림차순으로 온다. 최신이 배열 앞이다.
- `sender` 는 `{ type, member: { organizationMemberId } }` 이고 **이름이 없다.**

같은 시험에서 대화방 목록 쪽 동작도 확인했다.
**`GET /messenger/v1/channels` 는 `size` 를 완전히 무시한다.** `size=3` 이든 `1000` 이든 전체가 온다.
이미 있는 호출이라 이번에 바꾸지는 않았고, 사실만 남긴다.

**공식 문서에 없는 endpoint 다**:

2026-09-21 에 공식 문서를 화면으로 열어 Messenger > Channels 절을 확인했다.
그 절에 실린 endpoint 는 11개이고 `GET /messenger/v1/channels/{channel-id}/logs` 는 없다.
`GET` 으로 실린 것은 `/messenger/v1/channels` 하나뿐이다.
같은 경로의 `POST` 와 `PUT` 과 `DELETE` 는 실려 있는데 `GET` 만 빠져 있다.

스냅샷이 낡아서 빠진 것이 아니라 문서가 이 경로를 싣지 않는다.
ADR-046 이 정한 근거 우선순위대로 공식 문서를 확인한 결과이므로 이 항목은 여기서 매듭짓는다.

**그래서 예고 없이 막히거나 응답이 바뀔 수 있다.** 문서에 실린 경로와 달리 호환을 약속받지 못한다.
이 사실을 `README.md` 와 `skills/dooray-cli/SKILL.md` 와 `logs` 의 명령 설명에 적어,
쓰는 사람이 자동화에 넣기 전에 알 수 있게 했다.

`scripts/api-endpoint-inventory.mjs` 는 이 경로를 「문서에 없는 줄 알고 쓰는 것」 목록에 두고
「구현에 있고 공식에 없는 것」 에서 뺀다. 그 목록이 비어야 정상이라는 판정을 지키기 위해서다.
목록과 사유는 그 스크립트가 소유한다.

저장소가 이 경로를 이번에 처음 만난 것은 아니다.
ADR-051 의 표가 `messenger/v1/channels/{id}/logs` 의 응답 `id` 표기를 이미 기록하고 있다.
`direct-send` 와 달리 이 경로는 식별자를 문자열로 주므로 정밀도 손실이 없다고 적혀 있다.

**설계 결정**:

- **상한 초과는 조용히 자르지 않고 거부한다.** `-n 1001` 은 `EXIT_PARAM_ERROR` 로 끝낸다.
  1000건으로 잘라 주면 사용자는 그 이전 메시지가 없다고 오해한다.
  `hasMore` 가 항상 `true` 인데 가져갈 수단이 없으므로, 한계를 명시적으로 알리는 편이 정확하다.
  검증은 API 호출 전에 둬서 거부될 요청이 네트워크를 타지 않게 한다.
- **표와 `--quiet` 은 대화 순서로 뒤집고 `--json` 은 서버 순서를 유지한다.**
  사람은 위에서 아래로 읽고, 기계는 서버 응답 원형을 기대한다 (ADR-031 의 raw 출력과 같은 취지).
  두 순서가 다르다는 것을 `SKILL.md` 와 `README.md` 에 적었다.
- **발신자 이름은 표 모드에서만 해석한다.** `sender` 에 이름이 없어 `common/v1/members/{id}` 를 따로 부른다.
  고유 id 마다 한 번씩만 부르고, 실패한 id 는 그 자리에 id 를 그대로 보여준다.
  `--json` 과 `--quiet` 은 이름이 필요 없으므로 이 호출을 건너뛴다.
- **시각은 `Date` 로 파싱하지 않는다.** 파싱하면 서버가 준 offset 기준 시각이 실행 장비의 타임존으로 밀린다.
  다만 offset 을 떼는 것은 `+09:00` 일 때뿐이다. 그 밖의 offset 이나 `Z` 를 떼면 그 시각을 KST 로 오독하므로
  원형 문자열을 그대로 보여준다. 확인한 응답은 모두 `+09:00` 이었고, 다른 offset 이 오는 경우는 보지 못했다.
- **`hasMore` 가 `true` 면 stderr 로 알린다.** `-n` 을 1000 으로 채워 받은 사용자가 더 오래된 메시지의 존재를
  모르면, `-n 1001` 을 막아 예방하려던 오해가 그대로 남는다. 데이터가 아니라 안내이므로 stdout 을 오염시키지
  않는다. `--json` 과 `--quiet` 에서도 나간다.

**대안 기각**:

- **`-n` 상한 초과를 1000 으로 제한** — 잘렸다는 사실이 출력에 드러나지 않아 더 오래된 메시지가 없는 것처럼 보인다.
- **`--since` 같은 날짜 필터** — API 가 날짜를 무시하므로 클라이언트에서 필터링하는 것이 된다.
  최근 1000건 안에 그 날짜가 없으면 조용히 빈 결과가 나와, 범위 밖이라는 사실과 구분되지 않는다.
  필요하다면 별도로 다룬다.
- **`--json` 도 대화 순서로 뒤집기** — 원형 유지를 깨뜨린다. 자동화는 `seq` 로 직접 정렬할 수 있다.
- **모든 모드에서 발신자 이름 해석** — 발신자 수만큼 추가 호출이 붙는다. 이름이 쓰이지 않는 모드에서는 낭비다.
