## ADR-049: `getConfig` 가 부재와 손상과 읽기 실패를 구분해 돌려준다

- **status**: `accepted`

- **결정**: `getConfig` 의 반환형을 판별 가능한 결과 객체로 바꾼다.
  `absent`, `invalid`, `unreadable`, `ok` 네 상태를 구분한다.
  호출부 일곱 곳을 모두 고쳐 각 상태를 명시적으로 다루게 한다.

  캐시 무효화 판정은 `absent` 와 나머지를 다르게 본다.
  파일이 없으면 지울 근거가 없고, 읽지 못했으면 이전 계정을 알 수 없으므로 보수적으로 지운다.

  `JSON.parse` 결과에 타입 가드를 둔다. `as Config` 단언을 쓰지 않는다.

- **맥락**: `getConfig` 가 세 상황을 하나로 뭉갠다 (Issue #151).

  ```ts
  try {
    const raw = await readFile(CONFIG_PATH, "utf-8");
    return JSON.parse(raw) as Config;
  } catch {
    return null;
  }
  ```

  `null` 이 되는 경우가 셋이다.
  파일이 없는 정상적인 미설정 상태, JSON 파싱이 실패한 손상 상태, 권한이나 입출력 문제로 읽지 못한 상태다.
  호출부는 `null` 을 「설정이 없다」로만 해석한다.

  잘못된 판단이 세 곳에서 나온다.

  `getConfigOrThrow` 가 손상된 파일에 「설정이 완료되지 않았습니다. `dooray setup`」 을 안내한다.
  권한 문제라면 `setup` 도 저장에 실패하는데 사용자는 그 원인을 알 방법이 없다.

  캐시 무효화 판정이 어긋난다. `src/services/config.ts:59` 가 `prev` 를 `getConfig` 로 읽고
  `shouldInvalidateCache` 에 넘긴다. 그 함수는 이전 설정이 없으면 `false` 를 돌려주는데,
  손상된 파일도 같은 경로를 탄다. 그래서 손상된 상태에서 `apiKey` 를 바꾸면 이전 계정의 캐시가 남는다.
  캐시 디렉터리가 계정별로 나뉘지 않으므로 (ADR-042) 다음 조회가 다른 계정의 데이터를 쓴다.

  `clearMailCredentials` 가 손상된 파일에서 `false` 를 돌려준다.
  자격 증명이 남아 있는데 없었다고 보고하는 것이라, 지운 줄 알고 넘어간다.

  같은 파일의 `src/services/config.ts:63` 은 저장 **뒤** 되읽기 실패를 이미 경고로 다룬다.
  그 주석이 「`getConfig` 가 모든 오류를 `null` 로 삼키므로」라고 원인을 적고 있다.
  대응이 저장 뒤에만 있고 저장 앞의 `prev` 에는 없다.

  `JSON.parse(raw) as Config` 는 런타임 형태를 확인하지 않는다.
  필드가 빠졌거나 타입이 다른 파일도 통과하고 후속 호출에서 다른 자리의 오류로 나타난다.
  이 저장소는 같은 패턴을 `docs/pitfalls/code-review/json-parse-as-type-assertion.md` 로 정리해 두었다.

- **왜 반환형을 바꾸는가**: 별도 함수를 두면 기존 호출부가 그대로 돌아 파급이 없다.
  그러나 구분이 필요한 자리에서 새 함수를 부르는 것을 사람이 기억해야 한다.
  이번에 발견된 세 오판이 모두 그 종류다. 아무 검사도 잡지 못했다.
  반환형을 바꾸면 타입 검사가 모든 호출부에 구분을 강제한다.

- **왜 읽기 실패에서 캐시를 지우는가**: 이전 계정을 알 수 없는 상태다.
  지우지 않으면 다른 계정의 데이터가 남고, 그 증상이 조용하다.
  `resolveProject` 가 이전 환경의 projectId 를 돌려주고 그 id 로 새 환경에 요청을 보낸다.
  지우면 다음 조회가 API 를 다시 호출해 느려질 뿐이다. 두 비용이 대칭이 아니다.

- **대안 기각**:
  - 별도 함수를 둔다. 위에 적은 대로 구분을 사람이 기억해야 한다.
  - 예외를 던진다. 파일 부재가 정상 상태인데 예외로 만들면 모든 호출부가 `try` 로 감싸야 한다.
    `getConfigOrThrow` 가 이미 그 역할을 맡고 있어 층이 겹친다.
  - `null` 을 유지하고 두 번째 반환값으로 이유를 준다.
    호출부가 이유를 무시해도 컴파일된다. 강제하지 못하면 지금과 같다.
  - 스키마 검증 라이브러리를 넣는다. `Config` 는 평평한 객체 열두 필드다.
    타입 가드 함수 하나로 충분하고, 검사가 `pnpm install` 앞에서 도는 스크립트와 달리
    런타임 의존이라 넣을 수는 있지만 대가가 이득보다 크다.

- **결과**:
  - 얻는 것: 손상된 설정 파일에 `dooray setup` 을 안내하지 않는다.
    `doctor` 가 「파일이 손상됐다」와 「설정이 없다」를 다르게 안내한다.
    손상된 상태에서 계정을 바꿀 때 이전 계정의 캐시가 남지 않는다.
    `clearMailCredentials` 가 읽지 못한 것과 자격 증명이 없던 것을 구별한다.
    필드가 빠진 설정 파일이 후속 호출까지 가지 않는다.
  - 감당할 것: 호출부 일곱 곳을 모두 고친다.
    `src/index.ts`, `src/commands/setup.ts`, `src/commands/doctor.ts`, `src/commands/config.ts`,
    `src/services/config.ts` 와 `src/config/store.ts` 안의 두 곳이다.
    읽기 실패에서 캐시를 지우므로, 일시적인 입출력 오류가 캐시를 비우는 경우가 생긴다.
    다음 조회가 느려지는 것이 그 대가다.

- **적용 범위**: `src/config/store.ts` 가 결과 타입과 타입 가드를 소유한다.
  `getConfigOrThrow` 의 시그니처는 바뀌지 않는다. 안내 문구만 상태별로 갈린다.

  `~/.dooray/config.json` 의 스키마는 바뀌지 않는다. 읽는 방식만 바뀐다.
  마이그레이션이 필요 없다.
