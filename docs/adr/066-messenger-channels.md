## ADR-066: 대화방 목록을 `messenger channels` 로 두고 필터·정렬은 클라이언트에서 한다

**결정**: `GET /messenger/v1/channels` 를 `dooray messenger channels` 로 감싼다.
`--type` `--search` `--since` `--all` 을 받고, 필터링과 정렬은 모두 응답을 받은 뒤 클라이언트에서 한다.
보관된 방, 숨긴 방(`displayed: false`), `status` 가 `normal` 이 아닌 방은 기본에서 빼고 `--all` 로 포함한다.
정렬과 `--since` 는 `updatedAt` 을 쓰고, 이름과 도움말에서는 이 필드를 「수정 시각」 으로만 부른다.
제목이 빈 방은 나를 뺀 참여자 이름으로 표시명을 만든다. `--search` 는 표시명이 아니라 제목,
제목이 없으면 나를 뺀 참여자 각각의 실제 이름에서 찾는다.

**맥락**: 메신저 명령은 `send` `channel-send` `thread-send` `logs` 가 있었지만 대화방 목록을 보는 명령이 없었다.
`logs <channel>` 이나 `channel-send --channel` 에 넘길 channelId 를 CLI 안에서 찾을 수 없었고,
최근 대화가 있었던 방을 훑을 수단도 없었다.

endpoint 는 `resolveMessengerChannel` 이 이름 해석에 이미 쓰고 있었다(ADR-033).
그 해석은 제목이 빈 방을 후보에서 빼므로 1:1 방은 이름으로 넘길 수 없고 id 를 알아야 한다.
이 명령이 그 id 를 얻는 경로다.

이 endpoint 는 공식 API 문서의 Messenger > Channels 절에 실려 있다(ADR-061 이 2026-09-21 에 확인).
`scripts/api-endpoint-inventory.mjs` 의 대조도 이미 통과하는 경로라 ADR-062 의 조건은 해당하지 않는다.

**공식 문서가 정한 것** (`GET /messenger/v1/channels` 절, 2026-10-01 PR 리뷰에서 메인테이너가 확인):

- `type` 은 `direct`(1:1), `private`(일반 채널), `me`(나와의 대화), `bot`(봇이 만든 채널) 네 가지다.
- `displayed` 는 응답 예시에 `"displayed": true, /* 숨기기 여부 */` 로 실려 있다.
  이 주석만으로는 `true` 가 숨김인지 `false` 가 숨김인지 정해지지 않는다. 방향은 아래 실측으로 정했다.
- `status` 는 `system`, `normal`, `archived`, `deleted` 네 가지다.
- `updatedAt` 은 필드만 있고 무엇이 바뀔 때 갱신되는지는 적혀 있지 않다.

**실측으로 확인한 것**:

실제 계정으로 호출해 응답을 집계했다. 접근 가능한 대화방은 230개였다.

- **`size` 를 완전히 무시한다.** `size=3` 이든 `1000` 이든 전체가 온다(ADR-061 에도 기록). 페이징 수단이 없다.
- `type` 은 `direct`(1:1) 144개, `private`(그룹) 86개였다. 문서의 네 값 중 `me`·`bot` 인 방은 이 계정에 없었다.
- `status` 는 `normal` 229개, `system` 1개였다. 문서의 `archived`·`deleted` 는 보지 못했다.
- `archivedAt` 이 있는 방이 2개였다.
- `displayed` 는 `true` 227개, `false` 3개였다.
- **`displayed` 방향 실측 (2026-10-13).** 메신저에서 그룹(`private`) 방 하나를 「숨기기」 한 직후 `channels --all --json` 을 다시 받았다.
  그 방의 `displayed` 가 `true` → `false` 로 바뀌었고 `false` 인 방은 17개 → 18개가 되었다(늘어난 1개가 그 방이다).
  기본 목록의 `--search` 로는 그 방이 찾히지 않았다. `false` 가 숨긴 방이라는 해석이 확인됐다.
  같은 방의 숨김을 해제하자 `displayed` 가 `false` → `true` 로 돌아왔고 `false` 인 방은 18개 → 17개가 되었다.
  숨기기 `true` → `false`, 해제 `false` → `true` 양방향을 실측했다(2026-10-13).
- **`title` 이 빈 방이 154개다.** 1:1 방 144개 전부와 그룹방 10개다.
- `users.participants` 는 `{ type, member: { organizationMemberId } }` 의 배열이고 **이름이 없다.**
  `me` 는 `{ type, member: { organizationMemberId }, role }` 이다.
- `updatedAt` 은 밀리초가 붙은 ISO8601 이다(`2026-09-18T11:38:11.842+09:00`). 확인한 값은 모두 `+09:00` 이었다.
- 그 밖의 키는 `id` `capacity` `createdAt` `organization` 이다.
- **실측한 방에서는 `updatedAt` 이 그 방 최신 메시지의 보낸 시각과 같았다.** `updatedAt` 상위 12개 방에서
  `updatedAt` 과 `GET .../logs?size=1` 의 최신 `sentAt` 을 견줘 12개 모두 초 단위까지 일치했다.
  12개 표본의 관찰일 뿐이고 문서가 갱신 조건을 정하지 않으므로, 방 설정 변경 같은 다른 일로도 갱신되는지는 알 수 없다.

**설계 결정**:

- **필터링과 정렬은 클라이언트에서 한다.** API 가 파라미터를 받지 않으므로 다른 선택지가 없다.
  어차피 전체가 한 번에 오므로 클라이언트에서 필터링해도 누락이 생기지 않는다.
  ADR-061 이 `logs` 에서 `--since` 를 기각한 이유(최근 1000건 밖은 조용히 빠진다)가 여기에는 해당하지 않는다.
- **정렬은 `updatedAt` 내림차순이다.** 최근에 손댄 방을 위로 올리는 데 쓸 수 있는 시각 필드가 이것뿐이다.
  `updatedAt` 이 없거나 읽을 수 없는 방은 맨 뒤로 보내고, `--since` 를 주면 뺀다.
- **`updatedAt` 은 이름과 도움말에서 「수정 시각」 으로만 부른다.** 문서는 갱신 조건을 정하지 않으므로
  이름과 도움말은 필드 뜻만큼만 쓴다. 메시지 시각과 같았다는 위 실측을 근거로 「최근 활동」 이라 부르면
  문서에 없는 동작을 약속하게 된다. 표 머리는 `수정 시각`, 명령 설명과 `--since` 도움말은 `updatedAt(수정 시각)` 기준으로 쓴다.
- **기본 목록에서 보관된 방(`archivedAt` 있음), 숨긴 방(`displayed: false`), `status` 가 `normal` 이 아닌 방
  (`system`·`archived`·`deleted`)을 뺀다.** `--all` 이면 모두 남긴다.
  `displayed` 는 문서가 「숨기기 여부」 라고만 적어 방향을 정하지 않은 필드이고, 방을 숨겼을 때 `true` → `false` 로 바뀐 실측대로 `false` 를 숨긴 방으로 읽는다.
  사용자가 숨긴 방은 보관된 방처럼 평소 목록에서 볼 일이 적은 방이라 같은 자리에 둔다.
  `status`·`displayed` 키가 아예 없는 방은 남긴다. 실측에서는 모든 방에 있었지만, 키가 빠졌다고 숨기면 이유를 알기 어렵다.
- **종류 열과 표시명 접두는 문서의 네 `type` 값을 따른다.** `direct`→`DM`, `private`→`그룹`, `me`→`나와의 대화`, `bot`→`봇` 이다.
  문서에 없는 값이 오면 그룹으로 뭉개지 않고 원문을 sanitize 해서 그대로 보인다. `--type` 의 선택지도 이 네 값이다.
- **`--since` 는 `YYYY-MM-DD`(그 날 로컬 00:00) 또는 offset 붙은 ISO8601 을 받는다.**
  형식과 실재성 검증, 서머타임을 고려한 로컬 자정 확장은 `src/utils/local-date.ts` 의 공용 함수를 쓴다.
  캘린더 `--from`·`post list` 의 기간과 같은 규칙이다. 잘못된 값은 설정 조회와 API 호출 전에 `EXIT_PARAM_ERROR` 로 끝난다.
  비교는 `Date.parse` 로 시각끼리 한다. offset 이 서로 달라도 같은 순간이면 같게 본다.
- **제목이 빈 방의 표시명은 나를 뺀 참여자 이름으로 만든다.**
  1:1 방은 `DM: 홍길동`, 그룹방은 `그룹: 가, 나, 다` 이고 3명을 넘으면 `외 N명` 을 붙인다.
  이름을 얻지 못한 참여자도 `외 N명` 에 센다. 이름을 하나도 얻지 못하면 `(상대 미확인)` / `(참여자 미확인)` 으로 두고,
  나만 있는 방은 `(나)` 로 둔다. 제목이 있는 방은 제목을 그대로 쓴다.
  `bot` 방은 그룹과 같은 규칙에 접두만 `봇:` 이고, `me` 방은 참여자와 상관없이 `나와의 대화` 다.
  문서에 없는 type 은 그룹 규칙에 원문 type 을 접두로 쓴다.
- **나는 목록 응답의 `me` 로 가리고, 내 이름은 조회하지 않는다.** 방마다 `me` 가 들어 있으므로 추가 호출이 없다.
  `me` 가 빠진 제목 없는 방이 하나라도 있을 때만 `ensureMe` 로 내 id 를 얻는다.
  그 조회가 실패해도 목록은 낸다. 그 방들은 나를 빼지 않은 채 보이고, stderr 로 한 줄 알린다.
- **`--search` 는 제목이 있으면 제목, 없으면 나를 뺀 참여자 각각의 실제 이름에서 찾는다.** 대소문자를 무시한 부분 일치다.
  사람 이름으로 1:1 방을 찾는 것이 흔한 쓰임새라 제목만 보면 1:1 방은 하나도 걸리지 않는다.
  표시명은 앞 3명만 담고 CLI 가 만든 문구(`DM:` `그룹:` `외 N명` `(상대 미확인)` `(나)`)가 섞여 있어 검색 대상으로 쓰지 않는다.
  표시명을 대상으로 하면 4번째 이후 참여자로는 찾을 수 없고, `확인`·`외` 같은 말이 엉뚱한 방에 걸린다.
- **기본 제외로 방이 빠졌으면 stderr 로 한 줄 알린다.** 숨긴 1:1 방만 있을 때 `--search 이름 --type direct --quiet` 가 빈 출력에 종료 코드 0 으로 끝나
  에이전트가 방이 없다고 읽는다. 이유별 수(숨김, 보관, 그 밖의 `status`)와 `--all` 안내를 내고, 결과가 0건이면 찾는 방이 그 안에 있을 수 있다고 덧붙인다.
  `--type`·`--since` 로 어차피 빠질 방은 세지 않는다. stdout 은 바꾸지 않아 `--json`·`--quiet` 출력은 그대로다.
  이름 resolver 의 「찾지 못함」 안내도 `channels --all` 을 가리킨다. `--all` 은 `status` 가 `deleted` 인 방도 포함한다.
  응답에 `type`·`id` 가 없는 방은 종류·id 칸을 비워 표가 죽지 않게 하고, `--quiet` 은 id 가 없는 방을 뺀다.
- **`--search` 에서 이름 조회에 실패한 참여자가 있으면 그 수를 stderr 로 알린다.**
  조용히 빠지면 사용자는 그 사람과의 방이 없다고 읽는다.
- **빈 검색어는 거부한다.** 앞뒤 공백을 떼고 비면 API 호출 전에 `EXIT_PARAM_ERROR` 로 끝낸다.
  셸 변수가 비어 `--search ""` 가 되면 모든 방이 걸려 검색하지 않은 것과 구분되지 않는다.
- **참여자 이름은 표 모드와 `--search` 가 있을 때만, 필요한 사람만 조회한다.** 응답에 이름이 없어 `common/v1/members/{id}` 를
  고유 id 마다 한 번씩 부른다(`buildOrganizationMemberNameMap`). 대상은 필터링을 마친 뒤 남은 제목 없는 방의 참여자이고,
  `--search` 가 없으면 방마다 화면에 나올 앞 3명만 부른다(`외 N명` 은 개수만 있으면 된다). `--search` 가 있으면 나를 뺀 전원을 부른다.
  `--json` 과 `--quiet` 은 이름을 쓰지 않으므로 `--search` 가 없으면 건너뛴다.
  실측 계정에서 전체 표 출력은 약 27초가 걸렸다. 제목 없는 방 154개 중 144개가 1:1 방이라 상대가 저마다 달라
  고유 조회 대상은 145명이고, 앞 3명 제한으로 줄어든 것은 1명이다. 시간 대부분은 클라이언트의 요청 속도 제한
  (버스트 20, 초당 5건)에서 나온다. 줄이려면 멤버 이름 캐시가 필요하고, 그것은 이번 범위 밖이다.
- **`--json` 은 필터·정렬만 적용한 서버 응답이고 표시명을 넣지 않는다.** raw 유지 규약(ADR-031, ADR-056)을 따른다.
- **시각은 `logs` 의 `formatSentAt` 으로 보인다.** `Date` 로 파싱하지 않고 `+09:00` 일 때만 offset 과 초·밀리초를 뗀다(ADR-061).
- 표의 모든 열(이름·종류·수정 시각·id)은 서버가 준 문자열에서 나오므로 표에 넣기 전에 `sanitizeForTerminal` 을 거친다.
  `formatSentAt` 은 형식이 다르면 원문을 그대로 돌려주므로 시각 열도 예외가 아니다. `--json`·`--quiet` 은 raw 그대로 낸다(ADR-031).

**대안 기각**:

- **`--search` 를 제목에만 적용** — 1:1 방 144개가 전부 제목이 비어 있어 사람 이름으로 찾을 수 없다.
- **`--search` 를 표시명 전체에 대조** — 접두어는 화면 표시용일 뿐 검색 대상이 아니다.
  `DM` 으로 1:1 방만 골라내는 쓰임새는 `--type direct` 가 맡는다. 4번째 이후 참여자를 못 찾는 문제도 있다.
- **`client.searchMembers({ name })` 로 검색어를 멤버 id 로 먼저 바꾸기** — 호출 수는 줄지만 서버 이름 검색이
  정확 일치일 가능성이 있어(확인하지 않음) 부분 일치를 잃을 수 있다. 성씨나 이름 일부로 찾는 쓰임새가 깨진다.
- **모든 모드에서 이름 조회** — 방이 많으면 수십~백여 번의 호출이 붙는다. 이름을 쓰지 않는 모드에서는 낭비다.
- **`--json` 에 표시명 끼워넣기** — raw 유지 규약을 깬다. 필요해지면 ADR-056 처럼 명시 옵션으로 연다.
- **`--since` 를 상대 기간(`7d` 등)으로도 받기** — 캘린더와 날짜 입력 규칙이 갈린다. 필요해지면 두 명령에 함께 더한다.
- **`displayed` 로 필터링하지 않기** — 처음에는 뜻을 가리지 못해 이 쪽을 택했다. 숨긴 방을 기본 목록에 내면 사용자가 숨긴 방이 다시 보인다. `--all` 로 볼 수 있으므로 기본에서 빼도 방을 잃지 않는다.
- **`me`·`bot` 을 그룹으로 표시** — 제목 빈 `me` 방이 `그룹: (나)` 로 보이는 등 문서의 type 뜻과 어긋난다.
- **표 머리와 도움말에 「최근 활동」 을 쓰기** — 12개 방 실측에 기댄 이름이다. 문서가 갱신 조건을 정하지 않아 근거가 없다.
