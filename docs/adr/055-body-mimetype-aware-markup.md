## ADR-055: 본문에 마크업을 넣고 빼는 경로는 그 본문의 mimeType 에 맞는 문법을 쓴다

- **status**: `accepted`

- **결정**: CLI 가 본문에 링크를 넣거나 빼는 경로는 그 본문의 `mimeType` 을 읽어 문법을 고른다.
  `text/x-markdown` 이면 지금의 마크다운 문법을 그대로 쓰고, `text/html` 이면 HTML 앵커를 쓴다.
  해당하는 경로는 다섯이다.

  | 경로 | 넣거나 빼는 것 |
  | --- | --- |
  | `post edit --mention` / `--mention-group` | 멤버와 그룹 멘션 |
  | `post edit --link-task` | 다른 업무로 가는 링크 |
  | `post comment edit --mention` / `--link-task` | 댓글의 멘션과 업무 링크 |
  | `post comment file upload` | 첨부 파일 reference |
  | `post comment file delete` | 첨부 파일 reference 제거 |

  `post create` 와 `post comment add` 는 이 다섯에 들어가지 않는다.
  두 명령은 본문 형식을 `text/x-markdown` 으로 고정해 보내므로 고를 것이 없다.
  이 결정은 기존 형식을 보존하는 경로만 다룬다.

  `text/html` 본문의 멘션을 어떤 태그로 표현하는지는 공식 API 문서로 확인한 표기를 쓴다.
  **공식 문서가 그 표기를 정의하지 않으면 그 경로는 거절한다.**
  종료 코드 3 으로 멈추고 `--mime-type` 으로 형식을 바꾸는 방법을 안내한다.
  확인되지 않은 표기를 추측해 넣으면 링크로 렌더링되지 않는 문자열이 남고, 그 사실이 출력에 드러나지 않는다.

- **맥락**: `post edit` 은 `resolveBodyMimeType` 으로 본문 형식을 이미 구해 두고도([ADR-053](053-body-mimetype-preservation.md))
  그 값을 마크업을 만드는 함수에 넘기지 않는다.
  `prependMentions` 와 `appendTaskLinks` 는 형식과 무관하게 `[이름](dooray://...)` 를 만든다.
  그래서 `text/html` 본문에는 마크다운 원문이 그대로 붙고, 링크로 렌더링되지 않아 멘션 알림도 가지 않는다.

  `post comment file upload` 의 `appendFileReference` 도 같은 구조다.
  HTML 댓글에 파일을 올리면 `[name](/files/<id>)` 이 평문으로 남아 첨부에 닿을 수 없다.

  빼는 쪽은 더 나쁘다. `removeFileReference` 의 정규식은 마크다운 전용이라 HTML 본문에서 앵커를 찾지 못한다.
  찾지 못해도 본문 갱신이 성공으로 처리되고 그 다음 단계가 파일을 삭제하므로,
  본문에는 대상이 사라진 링크가 남는다.

  [ADR-053](053-body-mimetype-preservation.md) 은 **기존 형식을 보존하는 것**까지 정했다. 보존한 형식에 맞는 내용을 만드는 것은 그 결정의 범위 밖이었다.

- **대안 기각**:
  - **지금 동작을 두고 경고만 낸다** — 경고를 낸 뒤에도 링크로 렌더링되지 않는 문자열이 본문에 남는다.
    빼는 쪽의 대상이 사라진 링크도 그대로 남아, 고치려던 것이 남는다.
  - **HTML 본문이면 무조건 거절한다** — 공식 문서가 표기를 정의하는 경우까지 막는다.
    `text/html` 업무에 파일을 올리는 것은 흔한 작업이고, 거절만 하면 CLI 로는 방법이 없다.
  - **본문을 마크다운으로 변환해 저장한다** — 표의 셀 배경이나 rowspan 으로 정보를 표현한 문서가 깨진다.
    [ADR-053](053-body-mimetype-preservation.md) 이 보존을 결정한 이유와 정면으로 어긋난다.
  - **`mimeType` 을 보지 않고 본문 내용으로 형식을 추측한다** — 두 형식 모두 평문을 담을 수 있어 구별되지 않는다.
    응답이 형식을 이미 알려주므로 추측할 이유가 없다.

- **결과**:
  - 얻는 것: `text/html` 업무와 댓글에서도 멘션 알림이 가고 첨부 링크가 닿는다.
    파일을 지울 때 본문의 링크도 함께 사라진다.
    표기를 확인하지 못한 경로는 종료 코드로 멈추므로, 호출하는 쪽이 실패한 사실을 알 수 있다.
  - 감당할 것: 마크업을 만드는 함수의 시그니처에 형식 인자가 붙고, 호출부가 그 값을 넘겨야 한다.
    넘기지 않으면 기본값으로 떨어지므로, 기본값을 `text/x-markdown` 으로 두어 종전 동작을 유지한다.
    HTML 표기가 공식 문서에 없을 때 거절하는 경로가 늘어, `text/html` 본문을 쓰던 자동화가 멈출 수 있다.

- **적용 범위**: `src/body/mention.ts`, `src/body/task-link.ts`, `src/body/comment-files.ts` 와
  그 셋을 부르는 `src/commands/post/edit.ts`, `src/commands/post/comment/edit.ts`,
  `src/commands/post/comment/file/upload.ts`, `src/commands/post/comment/file/delete.ts`.

**실측으로 확인한 것 (Issue #173, 2026-09):**

| 무엇 | `text/html` 표기 | 근거 |
| --- | --- | --- |
| 멤버 멘션 | 정하지 못했다 | 확인 못함 |
| 그룹 멘션 | 정하지 못했다 | 확인 못함 |
| 업무 링크 | 정하지 못했다 | 확인 못함 |
| 첨부 reference | 정하지 못했다 | 확인 못함 |

넷이 모두 `확인 못함` 이므로 `text/html` 본문의 네 경로는 모두 거절한다.
`src/body/body-markup.ts` 의 `HTML_SUPPORTED_KINDS` 가 그 목록을 코드에서 소유한다.
표기를 확정하면 이 표를 고치고 그 목록에 종류를 더한다.

**어떻게 확인했는가:**

1. 공식 API 문서를 열어 본문 전문을 검색했다.
   정의된 것은 본문 `mimeType` 이 받는 값 둘(`text/html` 과 `text/x-markdown`)뿐이다.
   `dooray://` 와 `멘션` 과 `mention` 이 한 건도 나오지 않는다.
   `text/x-markdown` 쪽 표기도 문서에는 없다. 지금 CLI 가 쓰는 마크다운 표기는 실동작으로 굳은 것이다.
2. 개인 프로젝트의 업무 18건을 조회해 본문 형식을 모두 읽었다. 전부 `text/x-markdown` 이다.
   **Dooray 웹 편집기는 `text/html` 본문을 만들지 않는다.**
   그래서 화면에서 멘션을 넣고 저장된 본문을 역으로 읽는 방법이 성립하지 않는다.
3. 사내 프로젝트 셋의 최근 업무를 훑어 `text/html` 본문을 한 건 찾았다.
   메일을 업무로 받은 것이고 `dooray://` 도 `/files/` 도 들어 있지 않다.
   **`text/html` 본문은 메일 수신 경로에서 생긴다.**
4. 개인 프로젝트에 임시 업무를 만들어 `text/html` 본문에 표기 여섯을 넣고 다시 받아 대조했다.
   마크다운 표기 셋과 앵커 표기 셋이다. 줄 끝 개행 하나 말고는 보낸 것과 같았다.
   **서버는 `text/html` 본문을 그대로 저장하고 앵커를 고치지 않는다.** 댓글도 같다.
5. 그 업무를 Dooray 화면에서 열어 확인했다. 그 결과가 아래다.

**5번에서 알아낸 것과 알아내지 못한 것:**

- 마크다운 표기 셋은 렌더링되지 않는 것으로 본다.
  화면을 본 사람이 그 셋을 언급하지 않았다
- 앵커 표기 셋의 결과는 아래와 같다. 화면을 본 사람의 표현을 그대로 옮긴다.

  | 앵커 표기 | 화면 |
  | --- | --- |
  | 멘션 | 멘션으로 보인다 |
  | 업무 링크 | 링크처럼 보이기는 하나 Dooray 업무 링크 형식과 다르다 |
  | 첨부 | 보이기는 하나 링크가 의도와 다르다 |

  **눌렀을 때 어디로 가는지는 확인받지 못했다.** 멘션의 알림이 실제로 가는지도 확인하지 못했다.
  앵커 멘션에 쓴 표기는 `<a href="dooray://<orgId>/members/<memberId>" title="me">@이름</a>` 형태다.
  그룹 멘션은 이 실측에 넣지 않았다
- 댓글 본문의 표기 셋은 확인하지 못했다.
  화면 확인이 업무 본문까지만 이뤄졌다

**그래도 넷을 모두 `확인 못함` 으로 둔다.**

멤버 멘션은 화면에 멘션으로 보이는 것까지 확인했다. 그것만으로는 분기를 열지 않는다.
멘션의 값은 알림이 가는 것이고, 그 알림은 확인하지 못했다.
보이기만 하고 알림이 가지 않으면 호출하는 쪽은 멘션했다고 믿은 채 상대는 모르게 된다.
평문으로 남는 것보다 나쁘다.

업무 링크와 첨부는 앵커로 보이기는 하나 Dooray 고유 동작이 아니다.
링크가 걸린 것처럼 보이면서 업무나 첨부에 닿지 않는 쪽도 같은 이유로 지원한다고 말할 수 없다.

그룹 멘션은 실측에 넣지 않아 근거가 없다.

**댓글 경로는 본문이 확정되더라도 따로 확인한 뒤에 연다.**
본문에서 통하는 표기가 댓글에서도 통한다는 것은 확인된 바 없다.
`post comment edit` 의 멘션과 업무 링크, `post comment file upload` 가 여기 해당한다.
본문 쪽이 먼저 열리면 같은 `text/html` 인데 `post edit` 에서 되는 것이
`post comment edit` 에서 거절되는 차이가 생긴다.
그 차이는 근거의 차이에서 오는 것이지 Dooray 의 동작 차이가 확인된 것이 아니다.

**다시 확인할 때 할 일:**

개인 프로젝트에 `text/html` 본문의 업무를 만들고 앵커 표기 넷을 한 줄씩 넣는다.
`<a href="dooray://<orgId>/members/<memberId>" title="me">@이름</a>` 형태와
그룹 멘션 형태와 `tasks/<postId>` 형태와 `/files/<fileId>` 형태다.
**화면에서 넷을 하나씩 눌러 어디로 가는지 적는다.** 멘션은 상대에게 알림이 실제로 가는지까지 본다.
그것이 이번에 모자랐던 근거다.
같은 셋을 댓글 본문에도 넣어 업무 본문과 같은지 본다.
확인이 끝나면 그 업무를 지운다.

**빼는 쪽은 거절하지 않는다.** `post comment file delete` 는 `text/html` 본문에서도
마크다운 정규식으로 참조를 찾아 지운다. 이 결정 전의 CLI 가 `text/html` 댓글에
마크다운 참조를 평문으로 남겼고, 거절하면 그것을 지울 방법이 CLI 에 없어진다.
