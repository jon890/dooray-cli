## ADR-064: `post list` 에 사람·상위 업무·기간·정렬 필터를 열고 기간과 정렬은 CLI 가 검증한다

**결정**: `post list` 에 옵션 일곱 개를 더한다. 업무 목록 API 가 이미 받는 파라미터를 그대로 옮긴다.

| 옵션 | API 파라미터 | 받는 값 |
| --- | --- | --- |
| `--from <member>` | `fromMemberIds` | `me`, 15자리 이상 id, 이메일, 프로젝트 멤버 이름 중 한 명 |
| `--to <member>` | `toMemberIds` | 위와 같다 |
| `--cc <member>` | `ccMemberIds` | 위와 같다 |
| `--parent <ref>` | `parentPostId` | 이 프로젝트의 업무 번호, `project/번호`, postId(15자리 이상 숫자) |
| `--created <range>` | `createdAt` | `A~B`, `A~`, `~B`, `prev-<N>d` |
| `--updated <range>` | `updatedAt` | 위와 같다 |
| `--order <field>` | `order` | `createdAt`·`postUpdatedAt`·`postDueAt` 과 각각의 `-` 내림차순 |

기간의 A·B 는 `YYYY-MM-DD` 또는 offset 이 붙은 ISO8601 이다.
기간과 정렬은 API 를 부르기 전에 검증하고, 서버가 받지 않거나 공식 문서에 없는 기간 형태는 문서에 있는 `A~B` 로 바꿔 보낸다.
멤버 옵션은 옵션마다 한 명만 받는다.

**맥락**: `DoorayApiClient.getPosts` 는 이 파라미터를 모두 받도록 이미 짜여 있었지만,
명령은 `--subject`·`--tag`·`--all`·`--page`·`--size` 만 꺼내 주었다.
"이번 주 내가 등록한 업무" 나 "어떤 업무의 하위 중 내 담당" 을 보려면 전부 받아서 클라이언트에서 필터링해야 했다.

**실측으로 확인한 것**:

`GET /project/v1/projects/{project-id}/posts` 를 개인 프로젝트에 읽기 전용으로 호출해 확인했다.

공식 문서의 기간 형태(DATE_PATTERN)는 `today`, `thisweek`, `prev-{N}d`, `next-{N}d`, `2021-01-01T00:00:00+09:00~2021-01-10T00:00:00+09:00` 다섯 가지다.
`A~`·`~B` 와 날짜만 준 범위는 문서에 없다. 멤버 파라미터는 `fromMemberIds={organizationMemberId}` 처럼 id 하나로 적혀 있고,
여러 id 를 넘길 때의 결합 규칙은 어디에도 없다(`toMemberSize` 설명의 `toMemberIds[0]` 한 줄뿐이다).

- **기간은 offset 이 붙은 ISO8601 범위만 받는다.**
  - `2026-09-01T00:00:00+09:00~2026-10-01T23:59:59+09:00` 과 시작만 준 `2026-09-01T00:00:00+09:00~` 은 동작한다.
    `Z` 와 소수 초(`.000`)가 붙은 값도 받는다.
  - **날짜만 준 범위 `2026-09-01~2026-10-01` 은 HTTP 400** `Invalid request param: createdAt=...` 이다.
  - **끝만 준 `~2026-09-01T00:00:00+09:00` 도 400** 이다. 공식 문서의 `A~B` 표기에서 기대할 수 있는 형태지만 받지 않는다.
  - 시작을 아주 이른 값으로 채운 `1970-01-01T00:00:00+00:00~B` 는 받고, 시작을 비운 것과 같은 결과를 준다.
    `0001-01-01T00:00:00+00:00` 과 `2000-01-01T00:00:00+09:00` 으로 채워도 건수가 같았다.
  - 끝을 아주 늦은 값으로 채운 `2026-09-01T00:00:00+09:00~2999-12-31T23:59:59Z` 는 시작만 준 `A~` 와 같은 10건이다.
    `~2100-01-01T00:00:00Z` 로 채워도 10건이다. `updatedAt` 도 `A~` 와 `A~2100-01-01T00:00:00Z` 가 같은 11건이다.
  - **끝을 `9999-12-31T23:59:59Z` 로 채우면 HTTP 500 `SERVER_DB_ERROR`** 다.
    `9999-12-31T14:59:59Z` 와 `9999-12-31T23:59:59+09:00` 은 200, `9999-12-31T15:00:00Z` 는 500 이다.
    서버가 KST 로 바꾼 값이 10000년이 되면 실패하는 것으로 보인다.
  - **시작과 끝이 같은 시각인 범위와 뒤집힌 범위는 400** 이다.
  - `abc` 같은 값은 400 이다.
- **`prev-<N>d` 는 받는다.** `prev-30d`·`prev-3650d` 는 동작하고 `prev-0d` 는 0건이다.
  `prev-1w` 처럼 일 단위가 아닌 값은 400 이다.
- **`updatedAt` 은 `createdAt` 과 같은 규칙이다.** ISO 범위, 시작만, `prev-30d` 가 동작하고,
  날짜만 준 범위와 끝만 준 범위는 400 이다.
- **경계는 초 단위로 비교되고 양쪽 모두 그 초를 포함하지 않는 것으로 보인다.**
  `createdAt` 이 `2026-09-18T01:24:04Z` 인 업무는 `...01:24:03Z~...01:24:05Z` 에는 잡히지만
  시작을 `01:24:04Z` 로 두거나 끝을 `01:24:04Z` 로 두면 빠진다.
  응답의 `createdAt` 에는 밀리초가 없어 서버가 밀리초까지 저장하는지는 알 수 없다.
- **`order` 는 `-createdAt`·`createdAt`·`-postUpdatedAt`·`postDueAt` 이 동작한다.**
  **`order=bogus` 나 `order=-updatedAt` 은 오류 없이 무시되고 기본 정렬로 온다.**
  기본 정렬은 `order` 를 주지 않은 것과 같은 `createdAt` 오름차순이다.
- **`fromMemberIds`·`toMemberIds`·`ccMemberIds` 는 셋 다 동작한다.** 없는 id 하나만 주면 0건이다.
- **여러 id 를 쉼표로 이었을 때의 결과는 관찰로만 남긴다.** 공식 문서에 결합 규칙이 없어 설계 근거로 쓰지 않는다.
  `fromMemberIds` 는 하나라도 맞는 업무가, `ccMemberIds`·`toMemberIds` 는 모두 맞는 업무가 왔다.

**설계 결정**:

- **기간 형식은 CLI 가 정하고 서버가 받는 형태로 바꿔 보낸다.**
  - 날짜만 준 A 는 그 날 `00:00:00`, B 는 그 날 `23:59:59` 로 넓히고 **그 날짜의** 지역 offset 을 붙인다.
    서버가 날짜만 준 범위를 400 으로 거절하기 때문이다.
  - `~B` 는 시작을 `1970-01-01T00:00:00Z` 로 채워 보낸다. 서버는 끝만 준 범위를 거절하지만
    사용자 입장에서 `A~` 를 받으면서 `~B` 를 받지 않을 이유가 없다. 업무가 1970년보다 먼저 만들어졌을 리 없다.
  - `A~` 는 끝을 `2999-12-31T23:59:59Z` 로 채워 문서에 있는 `A~B` 로 보낸다. 서버는 `A~` 도 받지만 문서에 없는 형태다.
    끝을 `9999-12-31T23:59:59Z` 로 채우면 500 이 나서 상한 근처를 피해 2999 로 둔다.
  - 뒤집힘 검사는 채운 **뒤에** 한다. `~1969-12-31` 과 `3000-01-01T00:00:00Z~` 는 채우고 나면 뒤집힌 범위라 거부한다.
  - `prev-<N>d` 는 손대지 않고 보낸다. 일 단위만 받으므로 정규식도 `prev-[1-9]\d*d` 로 좁힌다.
  - `prev-0d` 는 서버가 오류 없이 0건을 주므로 API 전에 거부한다. `--parent 42` 와 정렬 오타를 막은 것과 같은 이유로, 빈 결과가 실수를 숨긴다.
    앞자리가 0 인 `prev-007d` 도 같은 정규식에 걸려 거부된다. 쓸 이유가 없는 표기라 받지 않는다.
  - offset 없는 일시, 달력에 없는 날짜·시각, 물결표가 없거나 둘 이상인 값,
    **시작이 끝과 같거나 뒤인 범위**는 `EXIT_PARAM_ERROR` 로 끝낸다. 서버도 400 을 주지만
    `Invalid request param` 만으로는 무엇이 틀렸는지 알 수 없다. 같은 시각도 서버가 거절하므로 함께 막는다.
    날짜만 준 `2026-09-01~2026-09-01` 은 넓힌 뒤 하루 범위가 되어 통과한다.
- **날짜 해석은 캘린더와 같은 함수를 쓴다.** 그 날짜의 offset, 서머타임으로 자정이 없는 날,
  `2026-02-31` 같은 실재하지 않는 날짜의 판정은 `calendar event list` 가 ADR-063 에서 이미 정했다.
  그 순수 함수를 `src/utils/local-date.ts` 로 옮기고 캘린더와 `post list` 가 함께 쓴다.
  오류 문구와 옵션 이름, 한쪽만 준 값의 처리는 명령마다 달라 각 명령에 남긴다.
  캘린더는 한쪽만 주면 그 날 하루로 채우고, `post list` 는 열린 범위로 둔다.
  캘린더 API 는 양끝을 필수로 받고 업무 목록 API 는 시작만 준 범위를 받기 때문이다.
- **날짜만 준 B 는 `23:59:59` 로 둔다.** 끝 경계가 그 초를 포함하지 않는 것으로 보여 마지막 1초에 만든 업무는 빠질 수 있다.
  다음 날 `00:00:00` 으로 보내면 그 1초를 살리지만, 같은 입력을 캘린더와 다르게 넓히게 된다.
  시작 경계도 같은 이유로 `00:00:00` 의 1초를 놓치므로 끝만 고쳐서는 대칭이 맞지 않는다.
- **구분자는 공식 표기대로 `~` 를 쓴다.** `~B` 는 셸 틸드 확장에 걸린다. zsh 는 따옴표 없는
  `--created ~2026-09-30` 을 `no such user or named directory` 로 끊고 CLI 까지 오지 않는다.
  다른 구분자를 더 받는 대신 사용 문서에 따옴표를 쓰라고 적는다. 서버 표기와 어긋나는 문법을 하나 더 두면 둘 다 설명해야 한다.
- **정렬은 `.choices()` 로 막는다.** 서버가 모르는 값을 오류 없이 무시해서, 오타를 내면
  다른 순서의 결과를 받고도 알아챌 수 없다. 기본값은 지금과 같은 `-createdAt` 이다.
- **멤버 해석은 `post create`·`post edit` 의 `--to`·`--cc` 와 같은 `resolveMember` 를 쓴다.**
  id 는 존재를 확인하고, 이메일은 organization 에서 찾고, 그 밖의 값은 프로젝트 멤버 이름에서 찾는다.
  여기에 `me` 를 더한다. 목록 조회에서 가장 흔한 대상이 나 자신이라서다. `me` 는 API 키 주인의 id 다.
  `me` 는 대소문자를 가리지 않는다. `Me` 를 이름으로 넘기면 부분 일치로 이름이 Me 로 시작하는 다른 사람이 걸린다.
- **멤버 옵션은 옵션마다 한 명만 받는다.** 공식 문서가 id 하나만 적고 결합 규칙을 적지 않아서다.
  같은 옵션을 두 번 주면 설정 조회·스피너·API 전에 `EXIT_PARAM_ERROR` 로 끝낸다.
  조용히 마지막 값을 쓰면 사용자는 두 사람이 모두 걸렸다고 오해한다. 여러 명은 문서에 규칙이 실리면 연다.
- **멤버 옵션의 빈 값과 공백만 있는 값은 거부한다.** 값은 trim 한 뒤 해석하고, trim 해서 비면 설정 조회·스피너·API 전에 `EXIT_PARAM_ERROR` 로 끝낸다.
  빈 값을 빼고 넘어가면 `--from "$WHO"` 에서 변수가 비었을 때 필터 없는 전체 목록이 종료 코드 0 으로 온다.
  공백만 있는 값은 이름 부분 일치로 넘어가 이름에 공백이 든 멤버로 풀린다. 둘 다 사용자가 알아채지 못하는 잘못된 결과다.
- **멤버·상위 업무·태그 해석은 함께 돌리되 멤버 목록은 먼저 한 번 받는다.**
  다섯 해석은 서로 기다릴 이유가 없다. 다만 `resolveMember` 를 동시에 부르면 캐시가 빈 상태에서
  이름 입력마다 프로젝트 멤버 목록 전체(멤버 수만큼의 상세 조회)를 따로 받는다.
  이름 입력이 하나라도 있으면 목록을 먼저 받아 캐시를 채우고, id·이메일·`me` 만 있으면 받지 않는다.
  `me` 를 여러 옵션에 줘도 내 정보는 한 번만 조회한다.
- **멤버 옵션은 가변 인자로 받지 않는다.** `post create` 의 `--to <members...>` 처럼
  가변 인자로 받으면 뒤에 오는 값을 더 삼킬 수 있다. 두 번 준 것을 알아채려고 값은 모아 두고 개수를 본다.
- **`--parent` 의 짧은 숫자는 이 프로젝트의 업무 번호로 본다.** 15자리 미만 숫자는 `<project>` 의 업무 번호로 찾아 postId 로 바꾸고,
  15자리 이상 숫자는 postId 로, `<project>/<number>` 는 `post create --parent` 와 같은 `resolvePostRef` 로 푼다.
  그 밖의 값은 기간처럼 API·스피너 전에 `EXIT_PARAM_ERROR` 로 끝낸다.
  `post create --parent` 는 슬래시 없는 값을 검증 없이 postId 로 넘긴다. `post list` 에서 같은 규칙을 쓰면
  `--parent 42` 가 `parentPostId=42` 로 나가 오류 없이 0건이 된다. 목록은 결과가 비어도 실패로 보이지 않아 실수를 숨긴다.
  `post list` 는 프로젝트를 이미 받으므로 번호를 그 프로젝트의 업무로 읽는 것이 자연스럽다.
  postId 는 19자리라 15자리 경계로 번호와 겹치지 않는다. 멤버 id 판정과 같은 경계다.
  `post create` 의 해석은 이번 범위가 아니라 그대로 둔다. 같은 입력이 두 명령에서 달리 읽히는 차이는 남는다.
- **멤버·상위 업무 필터는 주지 않으면 키를 넣지 않는다.** `--tag` 와 같은 규칙이다.

**대안 기각**:

- **기간 문자열을 서버에 그대로 넘기기** — 날짜만 준 범위와 `~B` 가 400 이 된다.
  가장 손쉬운 입력이 실패하고 오류 문구는 원인을 말해 주지 않는다.
- **실측한 결합 규칙대로 여러 명 받기** — `from` 은 하나라도, `cc` 는 모두 맞는 업무가 왔지만 공식 문서에 없는 동작이다.
  서버가 규칙을 바꿔도 알 수 없고, 공식 문서에 없는 동작에 기대어 개발하지 않는다는 저장소 기준에 어긋난다.
- **`A~` 를 그대로 보내기** — 서버는 받지만 문서에 없는 형태다. 끝을 채워도 결과가 같으므로 문서에 있는 형태로 보낸다.
- **`~B` 를 받지 않기** — `A~` 는 되는데 `~B` 만 안 되는 이유를 사용자가 알 수 없다.
  이른 시작으로 채우면 서버가 받는다는 것을 실측으로 확인했다.
- **날짜 하나만 준 값(`--created 2026-09-01`)을 그 날 하루로 받기** — 편하지만
  `A~B` 형식과 섞이면 `2026-09-01` 이 "그 날 하루" 인지 "그 날부터" 인지 읽는 사람이 헷갈린다. 이번에는 범위 형식만 받는다.
- **캘린더의 `resolveTimeRange` 를 그대로 쓰기** — 한쪽만 준 값을 그 날 하루로 채우고 50일 상한을 건다.
  업무 목록에는 맞지 않는 두 규칙이라 공통 부분만 떼어 냈다.
- **정렬 값을 서버에 맡기기** — 400 이 아니라 기본 정렬이 돌아와 실수를 숨긴다.
- **`--parent` 를 `post create` 와 같이 슬래시 없으면 postId 로 보기** — `--parent 42` 가 오류 없이 0건을 낸다.
  사용자는 하위 업무가 없다고 읽는다.
- **멤버 옵션의 빈 값을 조용히 빼기** — 필터가 빠진 전체 목록이 성공으로 나와 실수를 숨긴다.
- **`me` 를 `post create`·`post edit` 에도 열기** — 이번 범위는 조회다. 쓰기 명령의 입력 규칙은 따로 정한다.
