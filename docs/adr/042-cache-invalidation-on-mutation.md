## ADR-042: 캐시된 엔티티를 바꾸는 호출은 services 계열이 맡고 그 안에서 캐시를 지운다

**결정**: 캐시의 유효성을 깨는 변경을 `src/services/` 의 함수로 감싼다.
그 함수가 변경 성공 직후 무효해진 캐시를 지운다.
명령 파일이 저장 계층을 직접 부르고 따로 캐시를 지우는 형태를 쓰지 않는다.

유효성을 깨는 변경은 두 가지다.

| 무엇 | 무효해지는 범위 | 담당 |
| --- | --- | --- |
| 캐시되는 엔티티를 바꾸는 API 호출 | 그 엔티티의 캐시 파일 하나 | `src/services/<엔티티>.ts` |
| 캐시가 어느 계정·환경의 것인지를 바꾸는 config 변경 | 전체 캐시 | `src/services/config.ts` |

`src/resolvers/` 는 읽기 전용으로 남긴다. 쓰기 함수를 넣지 않는다.

캐시 삭제가 실패해도 명령은 성공으로 끝낸다.
경고를 stderr 로 내고 `dooray cache clear` 를 안내한다.

**맥락**: `project tags create` 가 캐시되는 엔티티를 바꾸는 첫 명령이다 (Issue #146).
그전까지 API 쓰기 메서드 13개는 업무, 댓글, 위키 페이지, 첨부파일, 메시지만 다뤘고 셋 다 캐시하지 않았다.
그래서 이 규칙이 없었던 것이 아니라 필요한 상황이 처음 생겼다.

캐시 TTL 은 대부분 24시간이다 (`docs/data-schema.md` 의 TTL 설계 근거 표).
지우지 않으면 방금 바꾼 것을 다음 명령이 그만큼 보지 못한다.
태그의 경우 만든 태그를 `post create --tag` 가 24시간 찾지 못해, 태그를 만든 목적 자체가 무너진다.

두 번째 사례가 곧 온다. `POST /project/v1/projects/{id}/milestones` 가 공식 API 에 있고
단계도 캐시되는 엔티티라 같은 문제를 겪는다.

**왜 계열을 새로 만드는가**: `src/resolvers/` 의 파일 19개는 전부 읽기다.
사람이 쓴 문자열을 API 가 요구하는 id 로 바꾸고, 그 번역표를 캐시로 들고 있는 것이 이 계열의 일이다.
함수 이름의 접두어가 그 역할을 말한다: `ensure` 는 목록 확보, `resolve` 는 문자열을 id 로,
`lookup` 은 검증 없는 id 변환, `validate` 는 정책 검증, `parse` 와 `classify` 는 입력 형태 판별,
`merge` 는 기존값과 새값 병합이다.

여기에 `create` 와 `update` 를 넣으면 계열의 성격이 바뀐다.
쓰기가 하나뿐일 때는 감출 수 있지만, 위에 적은 대로 두 번째가 이미 예정되어 있고
태그 삭제와 프로젝트 생성이 API 에서 지원되면 더 늘어난다.
그때 `resolvers` 라는 이름이 그 안의 내용을 설명하지 못한다.

읽기와 쓰기를 계열로 가른다. 어느 계열에 넣을지가 이름으로 정해지고, 새 mutation 이 붙을 자리도 정해진다.

**config 변경이 전체 캐시를 무효로 만드는 이유**: 캐시 디렉터리는 `~/.dooray/cache` 하나이고
계정·환경별로 나뉘지 않는다. `apiKey` 가 바뀌면 계정이 바뀐 것이고 `baseUrl` 이 바뀌면
접속 환경(민간·공공·금융)이 바뀐 것이라, 남아 있는 모든 파일이 다른 곳의 데이터가 된다.

증상이 조용하다. `resolveProject` 가 이전 환경의 projectId 를 돌려주고 그 id 로 새 환경에 요청을 보낸다.
`me` 캐시는 24시간이라 가장 오래 남고 `orgId` 를 담아 멤버 검색에 쓰인다.

값이 실제로 달라졌을 때만 지운다. 같은 값을 다시 설정하는 것은 변경이 아니다.
이전 설정이 없는 최초 설정도 지우지 않는다. 지울 것이 없고 알릴 것도 없다.
`tenantName`, IMAP·SMTP 설정, `trackLastRun` 은 캐시가 무엇을 담는지에 영향을 주지 않아 대상이 아니다.

캐시를 지웠으면 사용자에게 알린다. 다음 조회가 API 를 다시 호출해 느려지는 이유가 되고,
계정을 바꾼 것이 의도였는지 사용자가 되짚을 수 있다.
지운 것이 없었으면 알리지 않는다. 그래서 `clearCache` 가 지운 것이 있었는지를 돌려주고,
판정과 안내를 그 값으로 가른다. 판정은 캐시가 유효한지를 묻고 안내는 알릴 일이 있었는지를 묻는다.

**`clearCache` 는 실패를 삼키지 않는다**: 원래 `rm` 을 `try/catch` 로 감싸고 주석에
"directory doesn't exist" 라고 적어 두었는데, `force: true` 가 이미 부재를 실패로 보지 않으므로
그 `catch` 가 실제로 가린 것은 권한 오류와 입출력 오류뿐이다.
지우지 못한 캐시를 지웠다고 보고하면 이 ADR 이 막으려는 상황이 그대로 남는다.

그래서 `clearCache` 는 원래 오류를 그대로 던지고, 부르는 쪽이 문맥에 맞게 처리한다.
`dooray cache clear` 는 사용자가 명시적으로 요청한 작업이라 실패를 에러로 노출한다.
`services` 의 무효화는 부수 작업이라 경고만 내고 원래 명령을 성공으로 끝낸다.

지울 캐시가 없었던 경우는 실패가 아니다. 사용자가 원한 상태가 이미 이뤄져 있다.
그래서 `clearCache` 는 세 결과를 구분한다. 지웠으면 `true`, 지울 것이 없었으면 `false`,
지우지 못했으면 던진다.

**왜 실패해도 성공으로 끝내는가**: 캐시를 지우는 시점에 원래 변경은 이미 성공했다.
태그 생성이라면 삭제 실패로 명령을 실패시키면 사용자가 다시 실행해 같은 태그를 한 번 더 만든다.
config 변경이라면 저장이 이미 끝났고, 실패로 만들면 `dooray config set` 을 쓰는 자동화가 깨진다.
두 경우 모두 경고를 stderr 로 내고 `dooray cache clear` 를 안내한다.

**대안 기각**:

- `api/client.ts` 의 쓰기 메서드가 스스로 캐시를 지운다.
  `api/client` 는 순수 HTTP 래퍼이고 비즈니스 로직을 두지 않는다는 규칙과 어긋난다.
  의존 방향도 `commands → resolvers + services → cache/store + api/client` 라서 역방향이 된다.
- `src/resolvers/` 에 쓰기 함수를 넣는다.
  파일이 새로 생기지 않는 대신 읽기 전용 계열에 쓰기가 섞인다.
  mutation 이 늘어나면 계열 이름이 역할을 설명하지 못한다.
- 명령 파일이 API 호출과 캐시 삭제를 나란히 한다.
  계열이 얇아 읽기는 쉽지만, 새 mutation 명령을 짜는 사람이 삭제를 부를 것을 기억해야 한다.
  잊어도 아무 검사가 잡지 못하고, 증상이 24시간짜리 지연이라 원인을 찾기 어렵다.
- 캐시 TTL 을 짧게 바꿔 자연히 반영되게 한다. 조회 전반이 느려진다.
  바꾼 쪽이 자기 캐시를 지우는 편이 범위가 좁다.
- 삭제 대신 갱신한다. API 호출을 하나 더 쓴다. 다음 조회가 어차피 채운다.

**적용 범위**: 파일 하나가 엔티티 하나를 담당한다. 태그는 `src/services/tag.ts` 다.
`services` 는 `resolvers` 를 의존하지 않는다. 이름을 id 로 바꾸는 일과 바꾸는 일은 따로이고,
둘을 조합하는 것은 명령 파일의 몫이다.

엔티티 하나가 캐시 파일 하나에 대응하므로 무효화는 그 파일 하나로 끝난다.
`~/.dooray/cache/` 아래 파일이 서로 같은 엔티티를 중복 보관하지 않는다는 뜻이고,
새 캐시를 추가할 때도 이 성질을 유지해야 이 규칙이 단순하게 남는다.
