## ADR-024: `dooray post comment file *` — post-level files API + 댓글 PUT 합성

**결정**: `comment file {list,upload,download,delete}`는 댓글 조회·수정 API와 post-level files API를 명령별로 조합한다.
업로드는 `png`, `jpg`, `jpeg`, `gif`, `webp`, `bmp`, `svg`, `avif`, `heic` 확장자를 대소문자 구분 없이 이미지로 분류한다.
이미지는 `![filename](/files/<fileId>)`를, 그 외 파일은 `[filename](/files/<fileId>)`를 넣는다.
`delete`는 두 마크다운 형식을 모두 제거한 뒤 파일을 삭제한다.
`list`는 댓글 응답의 `files`와 본문 마크다운 참조를 `id` 기준으로 합쳐서 보여주고, 이름·크기는 업무 단위 첨부 목록에서 채운다.

사용자 멘탈 모델은 "댓글 첨부"이지만 CLI가 관측할 수 있는 모델은 업무 파일과 댓글 본문 참조의 조합이다.

**맥락**: 댓글 전용 첨부 엔드포인트는 존재하지 않는다.
본문 참조 방식은 더 나은 방법을 못 찾은 우회가 아니라 공개 API로 가능한 유일한 경로다.

웹 UI로 댓글에 파일을 첨부하면 본문에는 아무 참조도 들어가지 않고 댓글의 `files`에만 연결이 생긴다.
이 `files`가 첨부 카드로 렌더되는 실제 연결이고, 본문 링크 방식은 첨부 카드가 아니라 일반 링크로 표시된다.
그런데 공개 API로는 이 연결을 만들 수 없다. 세 갈래를 모두 시험했고 전부 실패했다 (2026-08, v0.15.1).

- 댓글 생성·수정 요청에 `files` 또는 `fileIds`를 넣는 방식 — 요소 형태를 바꿔도 모두 저장되지 않는다
- 댓글 단위 업로드 엔드포인트 — `api`와 `file-api` 양쪽 모두 404
- 업무 단위 업로드에 `logId`를 붙이는 방식 — 업로드는 200이지만 댓글에 연결되지 않는다

**가장 주의할 점은 실패를 조용히 버린다는 것이다.** `files`를 넘겨도 `resultCode: 0`, `isSuccessful: true`를 돌려주고 조회하면 비어 있어, 호출하는 쪽에서 실패를 감지할 수 없다.
공식 `파일 업/다운로드 관련 API 가이드`(2026.05.21 갱신)도 업무·드라이브·위키 단위만 열거하며 댓글 단위가 없다.

조회는 반대로 가능하다. 댓글 **단건** 조회 응답에는 `files`가 있고, 댓글 **목록** 조회(`GET .../logs`)에만 이 키가 없다.
다만 단건 응답의 `name`과 `size`는 항상 `null`이라 업무 단위 첨부 목록으로 채워야 쓸 수 있다.

모든 파일을 이미지 마크다운으로 넣으면 비이미지 파일이 깨진 이미지로 렌더되어 클릭할 수 없으므로 파일 종류에 따라 참조 형식을 나눈다.

**트레이드오프 (수용)**:
- **원자성 부재**: 2단계 (`upload`, `delete`) 중 한 단계만 성공할 수 있다. 부분 성공 시 stderr 안내와 0이 아닌 종료 코드를 반환한다
- **fileId namespace 가 post-level**: 같은 fileId 가 여러 댓글에서 참조 가능 → `delete` 가 다른 참조를 broken link 화 가능. 의도 명확화 위해 단일 동작
- **조회에 추가 호출**: `list`가 이름·크기를 채우려면 업무 단위 첨부 목록을 한 번 더 조회해야 한다. 이 조회가 실패해도 목록은 출력하고 채우지 못한 값만 `-`로 표시한다
- **웹 UI 결과와 다른 표시**: CLI `upload`로 올린 파일은 첨부 카드가 아니라 본문 링크로 보인다. 위 맥락대로 첨부 카드를 만들 수단이 없다
- **확장자 기반 분류**: 실제 파일을 검사하지 않아 잘못된 확장자는 다르게 렌더될 수 있지만 추가 I/O와 MIME 판별 의존성을 피한다

**대안 기각**:
- 댓글 전용 엔드포인트 — 부재. 비공개 엔드포인트 역공학 위험과 유지보수 부담
- 모든 파일에 이미지 마크다운 사용 — 비이미지 파일이 깨진 이미지로 표시되고 열 수 없음
- MIME 또는 파일 내용 검사 — 업로드 전 추가 I/O와 판별 복잡도에 비해 파일명 확장자가 CLI 입력 계약에 충분
- markdown reference 제거 없이 파일만 삭제 — 본문 broken link 잔존 → UX 회귀
- 기존 `post file *` 안내 — 사용자가 댓글 ↔ post 본문 first attachment 구분 못함
