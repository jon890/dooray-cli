## ADR-060: 메일 답장은 입력 형식과 무관하게 확인을 거친다

- **status**: `accepted`

- **결정**: `mail reply` 는 세 입력 형식 모두에서 발송 전에 확인을 거친다.
  UID 직접 입력도 예외가 아니다.

  TTY 에서는 원본의 제목, 보낸사람, IMAP 도착 시각, UID 를 보여주고 기본값이 아니오인 확인을 묻는다.
  거절하면 발송 없이 정상 취소한다.
  `-y` 와 `--yes` 가 그 확인을 생략한다.
  non-TTY 에서 그 옵션이 없으면 설정 조회와 IMAP 접근 전에 `EXIT_PARAM_ERROR`(3)로 중단한다.

  이 규약은 [ADR-036](036-delete-confirmation-policy.md) 이 삭제 명령에 정한 것과 같은 모양이다.

- **맥락**: 확인은 mail id 와 메일 웹 주소로 준 경우에만 있었다.
  그 둘은 도착 시각으로 원본을 추정하므로 다른 메일이 선택될 수 있다는 것이 확인의 근거였다([ADR-040](040-mail-url-to-uid-lookup.md)).
  UID 는 추정이 아니라서 그 근거가 없었고, 확인 없이 바로 발송했다.

  추정 여부는 이 경로의 위험을 다 설명하지 못한다.
  UID 는 사람이 외워서 넣는 값이 아니라 `mail list` 결과에서 나오는 값이다.
  자동화와 에이전트가 목록에서 UID 를 얻어 `mail reply` 에 넘기는 흐름이 자연스럽고,
  그 흐름에서 잘못된 UID 를 집으면 의도하지 않은 상대에게 답장이 나간다.

  실제로 그렇게 나갔다. 문서 감사 중에 에이전트가 non-TTY 가드 동작을 확인하려고
  UID 직접 입력 경로를 실행했고 답장이 발송됐다.
  받는 쪽이 회신 불가 주소여서 수신 서버가 거부했을 뿐, 일반 주소였으면 그대로 전달됐다.

  발송은 되돌릴 수 없다. 그 점에서 삭제 명령과 성격이 같은데 이 경로만 규약 밖에 있었다.

- **실측으로 확인한 것**:
  발송분은 보낸메일함에 남지 않는다.
  `src/api/smtpClient.ts` 가 SMTP 발송만 하고 IMAP 보낸메일함에 저장하지 않는다.
  사고가 나도 보낸메일함으로는 무엇이 나갔는지 확인할 수 없다.
  이것이 사후 복구 수단이 없다는 뜻이므로, 사전 확인의 가치가 삭제 명령보다 낮지 않다.
  이후 [ADR-077](077-mail-save-sent.md)로 보낸메일함에 저장하게 됐다. 발송이 되돌릴 수 없다는 점은 그대로여서 사전 확인은 유지한다.

- **대안 기각**:
  - **UID 경로는 지금대로 두고 non-TTY 만 막는다** — 자동화 사고는 줄지만 세 입력 형식의 동작이 계속 다르다.
    어느 형식이 확인을 거치는지 외워야 하고, 오인하면 되돌릴 수 없는 발송이 그대로 나간다.
    `mail get` 과 `mail reply` 가 같은 입력을 받는다는 규약도 반쪽이 된다.
  - **추정 경로에만 확인을 두는 지금 기준을 유지한다** — 확인의 근거를 「원본이 맞는지」로만 본 것이다.
    되돌릴 수 없는 동작인지를 기준으로 보면 세 형식이 모두 같다.
  - **발송 전 확인 대신 발송 뒤 취소를 준다** — SMTP 에 그런 수단이 없다.
    보낸메일함에도 남지 않아 무엇을 취소할지 찾을 수도 없다.
  - **`mail send` 까지 함께 확인을 건다** — `mail send` 는 받는 사람을 호출하는 쪽이 직접 적는다.
    답장처럼 서버에서 찾은 값이 받는 사람이 되는 구조가 아니라 잘못 집을 여지가 다르다.
    이 결정의 범위 밖으로 둔다.

- **결과**:
  - 얻는 것: 세 입력 형식의 동작이 같아진다. 어느 것으로 불러도 발송 전에 한 번 멈춘다.
    자동화는 `-y` 를 명시해야 하므로, 확인 없이 보내는 것이 선택한 결과로 남는다.
    되돌릴 수 없는 명령의 규약이 삭제와 발송에서 하나가 된다.
  - 감당할 것: UID 로 답장하던 비대화형 자동화는 `-y` 나 `--yes` 를 더해야 한다.
    더하지 않으면 종료 코드 3 으로 멈춘다. ADR-036 이 삭제 명령에서 감수한 것과 같은 비용이다.
    TTY 에서 UID 로 답장하던 사람에게도 확인이 한 단계 늘어난다.
    확인 화면을 만들려면 원본을 먼저 받아야 하므로, UID 경로에도 `getMail` 호출이 확인보다 앞선다.
    그 호출은 종전에도 답장 제목과 `In-Reply-To` 를 얻으려고 하고 있었다. 왕복이 늘지는 않는다.

- **적용 범위**: `src/commands/mail/reply.ts` 의 확인 판정과 `--yes` 설명, non-TTY 오류 문구.
  `resolveMailTarget` 과 `resolveMailUid` 의 동작은 바꾸지 않는다.
  `mail get` 은 조회라서 이 결정의 범위 밖이다.
