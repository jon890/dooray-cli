## ADR-039: Dooray 요청 제한을 응답 헤더로 보정하는 클라이언트 토큰 풀

**결정**: `DoorayApiClient` 가 모든 요청을 토큰 버킷으로 통과시킨다.
버킷은 응답 헤더가 알려주는 서버 상태로 매번 보정하고, 429 를 받으면 남은 토큰을 비운 뒤 재시도한다.

**맥락**: Dooray 의 제한은 고정 초당 횟수가 아니라 토큰 버킷이며, 매 응답에 현재 상태를 실어 보낸다.

```
x-ratelimit-burst-capacity: 20
x-ratelimit-replenish-rate: 5
x-ratelimit-remaining: 19
```

즉 순간 20개까지는 즉시 통과하고 그 뒤로는 초당 5개씩만 충전된다.
이 구조를 모르면 두 방향 모두 틀린다.
제한을 무시하면 자식이 6개 넘는 위키 트리에서 항상 429 가 났고, 반대로 고정 초당 4회로 묶으면 멤버 이름 보강처럼 버스트로 끝나던 작업이 몇 배 느려진다.

병렬 호출 지점이 위키 트리 조회 외에도 여럿이라 호출부마다 상한을 두면 같은 사고가 다른 명령에서 반복된다.
그래서 클라이언트 한 곳에서 모든 요청이 같은 풀을 공유한다.

**대안 기각**:

- 호출부의 동시 요청 상한만 낮추기 — 동시 개수만 제한하고 간격을 두지 않으므로 짧은 작업이 연달아 끝나면 순간 요청률이 다시 상한을 넘는다. 다른 병렬 호출 지점도 그대로 남는다.
- 고정 초당 횟수로 묶기 — 버스트 여유를 못 쓴다. 서버가 알려주는 실제 잔량을 두고 추측값을 쓰는 셈이라, 제한 정책이 바뀌면 함께 틀린다.
- 429 재시도만 강화하기 — 동시 요청이 한꺼번에 429 를 받으면 재시도도 함께 몰려 같은 결과가 반복된다. 재시도는 보조 수단이지 제한 준수 수단이 아니다.

**적용 범위**: `ky` 인스턴스를 거치는 모든 요청에 적용된다.
파일 업로드·다운로드는 307 리다이렉트를 직접 다루느라 `fetch` 를 그대로 쓰므로 이 풀을 거치지 않는다.
호출 수가 적어 현재는 문제가 되지 않지만, 대량 첨부 작업을 추가하면 같은 풀에 태워야 한다.
