## ADR-063: 캘린더는 읽기 세 명령만 두고 기간은 항상 양끝을 보낸다

**결정**: `calendar list` 와 `calendar event list` 와 `calendar event get` 셋을 둔다.
일정 생성·수정·삭제는 두지 않는다. (이 부분은 [ADR-070](070-calendar-event-write.md)으로 대체됐다.)
`event list` 는 `--from` 과 `--to` 를 받아 **언제나 `timeMin` 과 `timeMax` 를 함께** 보낸다.
한쪽만 주면 빠진 쪽을 **준 값과 같은 날**로 채워, 단독 지정은 그 날 하루가 된다.

| 명령 | endpoint | 공식 문서 |
| --- | --- | --- |
| `calendar list` | `GET /calendar/v1/calendars` | 있다 |
| `calendar event list` | `GET /calendar/v1/calendars/*/events` | 있다 |
| `calendar event get` | `GET /calendar/v1/calendars/{calendar-id}/events/{event-id}` | 있다 |

**맥락**: 캘린더를 다루는 명령이 없었다. 회의 참석 여부를 확인하거나 기간 안의 일정을 모으는 일은
CLI 밖에서 따로 스크립트를 짜야 했다.

**공식 문서가 정한 것**:

캘린더 절의 표제는 「일정(이벤트) 목록 api(최대 1년치)」이고, 아래 내용이 함께 적혀 있다.

- 경로의 `*` 자리에는 calendar-id 가 들어갈 수 없고 **`*` 만 입력할 수 있다**
- `timeMin` 과 `timeMax` 는 **필수**다
- `timeMin` 은 그 시각 **이후(inclusive)**, `timeMax` 는 그 시각 **미만(exclusive)** 의 일정을 준다

이 경로가 저장소의 공식 endpoint 스냅샷에서 빠져 있었던 것은 스냅샷의 추출 정규식 문자 집합에
`*` 가 없어 경로가 `*` 앞에서 잘렸기 때문이다. 스냅샷에 남아 있던 `GET /calendar/v1/calendars/` 가
그 잘린 흔적이었다. 정규식과 스냅샷을 함께 고쳤다.

**실측으로 확인한 것**:

응답 형태와 파라미터 동작은 실제 호출로 확인했다.

- **한 번에 조회할 수 있는 기간은 50일이다.** 문서 표제의 「최대 1년치」와 다르다.
  `2026-01-01T00:00+09:00` 부터 50일째 `23:59:59` 까지는 통과하고, 51일째 `00:00` 부터는
  HTTP 400 과 `USER_INVALID_EXCEED_MAXIMUM_PERIOD` 가 온다. 1월·2월·3월 중순에서 시작해도 같았고,
  판정은 초가 아니라 날짜 단위로 보인다.
- **`timeMax` 의 exclusive 는 일반 일정에만 맞는다.** `timeMax=2026-09-22T00:00:00+09:00` 으로 보내면
  09-22 00:00 정각에 시작하는 일반 일정은 빠지는데, `startedAt` 이 `2026-09-22+09:00` 인 종일 일정은 포함된다.
  `timeMax=2026-09-21T23:59:59+09:00` 으로 보내면 둘 다 빠진다. 종일 일정은 날짜 단위로 비교되는 것으로 보인다.
- **목록은 참석자를 주지 않는다.** 문서는 목록 응답에 `users` 가 포함되지 않는다고 적고,
  실제로는 빈 객체 `{}` 가 온다. `calendar` 는 `{ id, name }` 뿐이다.
- **목록의 `me` 는 내가 참여자일 때만 채워진다.** 참여자면 `userType`(`from`·`to`·`cc`)과
  `status`(`accepted`·`declined`·`tentative`·`not_confirmed`)가 오고, 공유받은 캘린더의 남의 일정이면
  `{ type, member: { organizationMemberId } }` 뿐이다. 확인한 89건 중 87건이 후자였다.
  그래서 참여 여부는 상세 조회 없이 목록만으로 답할 수 있다.
- **상세에는 이름과 본문이 들어 있다.** `users.from` 은 객체 하나, `to` 와 `cc` 는 배열이고
  각 항목이 `{ type, status, member: { organizationMemberId, name, emailAddress } }` 다.
  `body` 는 `{ mimeType, content }` 다.
- **상세는 calendarId 자리에 `*` 를 받지 않는다.** `SERVER_GENERAL_ERROR` 가 난다. 두 id 가 모두 필요하다.
- **캘린더의 `me` 는 불린이 아니라 객체다.** `{ default, color, listed, checked, role, order }` 이고
  `role` 은 `owner`·`view`·`read_write`·`all` 이 왔다.
- `size` 와 `page` 는 무시된다. 페이징 수단이 없다.
- **잘못된 날짜 형식에 서버가 500 을 낸다.** `timeMin=2026-09-20` 처럼 offset 없는 값을 주면
  `Server error occurred. Please contact help@dooray.com` 이 온다. 서버에 형식 검증이 없다.

**종일 일정은 형식과 종료 해석이 모두 다르다**:

```
종일  startedAt: 2026-09-18+09:00          (T 시각이 없다)
종일  endedAt  : 2026-09-19+09:00
일반  startedAt: 2026-09-15T16:00:00+09:00
일반  endedAt  : 2026-09-15T17:00:00+09:00
```

`endedAt` 은 **그 날을 포함하지 않는다.** 위 일정을 날짜별로 조회해 확인했다.

| 조회 범위 | 그 일정이 잡히는가 |
| --- | --- |
| `2026-09-17` | 안 잡힌다 |
| `2026-09-18` | **잡힌다** |
| `2026-09-19` | 안 잡힌다 |

`endedAt` 이 `09-19` 인데 09-19 조회에 걸리지 않으므로, 이 일정의 실제 마지막 날은 `09-18` 하루다.
따라서 화면에 그릴 마지막 날은 `endedAt - 1일` 이다.

**설계 결정**:

- **기간은 항상 양끝을 보낸다.** 문서가 둘 다 필수로 정한다.
  둘 다 없으면 오늘 하루로 잡고, 한쪽만 주면 빠진 쪽을 **준 값과 같은 날**로 채운다.
  `--from 2026-10-01` 은 10월 1일 하루이지 "오늘부터 10월 1일까지" 가 아니다.
  ISO 값을 단독으로 주면 반대쪽 경계는 그 값의 날짜와 **그 값의 offset** 으로 세운다.
  지역 offset 을 붙이면 `--from 2026-10-01T20:00:00+00:00` 같은 입력에서 범위가 뒤집힌다.
- **날짜만 준 값은 `[그 날 00:00:00, 그 날 23:59:59]` 로 넓힌다.** 문서대로라면 `timeMax` 를
  다음 날 `00:00` 으로 두는 것이 정확하지만, 그러면 다음 날 시작하는 종일 일정이 경계에 걸려 섞여 나온다.
  연차·휴가 같은 종일 일정은 흔해서 "그 날 하루" 를 조회할 때마다 다음 날 종일 일정이 끼게 된다.
  `23:59:59` 로 두면 정확히 그 시각에 시작하는 일반 일정이 빠지지만 그런 일정은 사실상 없다.
  사용자가 기대하는 "그 날 하루" 에 맞는 쪽을 택한다.
  offset 은 고정값이 아니라 **그 날짜의** 것을 쓰고, 서머타임이 자정에 시작해 로컬 `00:00` 이
  없는 날은 `Date` 가 옮겨 놓은 실제 시각을 되읽는다.
- **입력은 API 호출 전에 막는다.** `YYYY-MM-DD` 와 offset 이 붙은 ISO8601 만 받는다.
  offset 없는 일시, 실재하지 않는 날짜·시각·offset(`2026-02-31T25:99:99+09:00`),
  양쪽을 다 주면서 뒤집은 범위, **50일을 넘는 범위**는 `EXIT_PARAM_ERROR` 로 끝낸다.
  기간 판정은 서버 실측에 맞춘다. 서버는 50일째의 끝(`23:59:59`)까지 받고 51일째 `00:00` 부터 거절하므로,
  `timeMax - timeMin` 이 51일 이상이면 거부한다. `--from 2026-01-01 --to 2026-02-20` 은 통과하고
  `--to 2026-02-21` 은 거부된다.
- **시각은 `Date` 로 파싱하지 않는다** (ADR-061 과 같은 이유). `+09:00` 일 때만 offset 을 떼고
  그 밖의 offset 이나 `Z` 는 원형을 보여준다. 종일 일정은 날짜만 오는 별도 형식이라 파서를 나눈다.
- **종일 일정은 기간으로 그린다.** 하루면 `2026-09-18 (종일)`, 여러 날이면
  `2026-09-18 ~ 2026-09-20 (종일)` 이다. 데이터가 어긋나 마지막 날이 시작보다 앞서면
  기간을 그리지 않고 시작 날짜만 낸다.
- **`event list` 표에 내 참여 여부를 낸다.** 목록의 `me.userType` 과 `me.status` 를 한국어로 옮겨 적고,
  내가 참여자가 아닌 일정은 비워 둔다. 참여 여부를 확인하려고 일정마다 상세를 열지 않아도 된다.
- **`event get` 표에 본문을 낸다.** 상세 조회에서만 얻을 수 있는 값이다.
  외부 문자열이라 제어문자는 치환하되 여러 줄 본문이 한 줄로 뭉개지지 않게 줄바꿈은 살린다.
  `mimeType` 이 `text/html` 이어도 변환하지 않고 원문을 보여준다.

**대안 기각**:

- **일정 생성·수정·삭제까지 제공** — 이번 요구는 조회와 참석 확인이다.
  수정과 삭제는 되돌리는 비용이 조회와 달라 확인 절차부터 따로 정해야 하므로 범위를 나눈다.
- **빠진 쪽을 오늘로 채우기** — 준 값이 오늘의 반대편에 있으면 `timeMin > timeMax` 가 되어
  조용히 0건이 나온다. `--from 2026-10-01` 처럼 앞으로의 일정을 묻는 가장 흔한 호출이 여기에 걸린다.
- **한쪽만 준 기간을 그대로 보내기** — 문서가 둘 다 필수로 정한다. 실측에서도 `timeMin` 만 준 결과가
  아무것도 주지 않은 것과 같았다. 사용자가 지정한 범위와 실제 조회 범위가 달라지고 결과만 보고는 알아챌 수 없다.
- **날짜만 준 `--to` 를 다음 날 `00:00` 으로 넓히기** — 문서의 exclusive 규정과 글자 그대로 맞지만,
  종일 일정은 날짜 단위로 비교돼 다음 날 종일 일정이 섞인다. 일반 일정 1초를 지키려다 흔한 종일 일정을 틀리게 보여준다.
- **잘못된 날짜를 서버에 맡기기** — 500 과 `help@dooray.com` 안내가 돌아온다.
  입력 실수인데 서버 장애처럼 보인다.
- **50일 상한을 서버에 맡기기** — 서버는 400 과 의미 있는 코드를 주므로 형식 오류만큼 나쁘지는 않다.
  그래도 다른 입력 검증과 같이 네트워크 앞에서 끊는 편이 일관되고, 오류 문구에 상한을 적을 수 있다.
- **종일 일정을 시작 날짜만 표시** — 장기 일정이 하루짜리로 보여 오독을 부른다.
- **참여 여부를 상세 조회로 판정** — 목록의 `me` 가 이미 답을 준다. 일정마다 상세를 열 이유가 없다.
- **상세에서도 멤버를 따로 조회** — 상세 응답에 이름이 이미 들어 있다.
