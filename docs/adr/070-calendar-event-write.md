## ADR-070: 캘린더 일정 생성·수정·삭제를 `event create`·`edit`·`delete` 로 둔다

**결정**: `calendar event` 아래에 쓰기 명령 셋을 더한다. ADR-063 의 "일정 생성·수정·삭제는 두지 않는다" 를 대체한다.

| 명령 | endpoint | 공식 문서 |
| --- | --- | --- |
| `calendar event create <calendar>` | `POST /calendar/v1/calendars/{calendar-id}/events` | 있다 |
| `calendar event edit <calendar> <event-id>` | `PUT /calendar/v1/calendars/{calendar-id}/events/{event-id}` | 있다 |
| `calendar event delete <calendar> <event-id>` | `POST /calendar/v1/calendars/{calendar-id}/events/{event-id}/delete` | 있다 |

`<calendar>` 는 캘린더 id 나 이름이다. 종일 여부는 `--start` 의 형식으로 정한다.
날짜만 주면 종일 일정이고 `--end` 는 **마지막 날(포함)** 이다. offset 이 붙은 일시면 일반 일정이고 `--end` 가 필수다.
생성은 `users`·`body` 키를 항상 싣고, 수정은 `--to`·`--cc` 중 한쪽만 주면 기존 값을 읽어 다른 쪽을 채운다.
수정은 반복 일정의 회차 id 를 받지 않는다.

**맥락**: ADR-063 은 조회와 참석 확인만 다루고, 쓰기는 확인 절차를 따로 정해야 한다는 이유로 미뤘다.
일정을 만들고 고치는 일도 CLI 밖에서 웹을 열거나 스크립트를 짜야 했다.

**공식 문서가 정한 것**:

- 생성과 수정은 같은 본문을 받는다. `subject`, `body{mimeType, content}`, `startedAt`, `endedAt`, `wholeDayFlag`,
  `location`, `users{to, cc}`, `recurrenceRule`, `personalSettings{alarms, busy, class}` 다.
- 종일 일정이면 `startedAt`·`endedAt` 을 `2015-09-08+09:00` 처럼 시각 없이 쓴다.
- `users` 항목은 `member{organizationMemberId}` 와 `emailUser{emailAddress, name}` 두 종류다.
- 수정은 **빈 값이 아닌 필드만** 반영한다. 반복 일정의 범위를 고르는 파라미터는 없다.
- 생성 응답은 `result{id}`, 수정·삭제 응답은 `result: null` 이다.
- 삭제는 `DELETE` 가 아니라 `POST .../delete` 이고 본문의 `deleteType` 이 `this`·`wholeFromThis`·`whole` 중 하나다.
  반복 일정의 한 회차는 `<eventId>-20240228T013000Z` 형태 id 를 경로에 그대로 넣는다.
- `recurrenceRule.until` 은 `datetime` 이라고만 적혀 있고 형식 예시가 없다.
- 알림 `trigger` 는 RFC 2445 형식(`TRIGGER:-PT10M`)이고 `action` 은 `mail`·`app` 이다.

**실측으로 확인한 것** (2026-10-19, 개인 캘린더):

- **생성은 `users` 와 `body` 키가 둘 다 있어야 한다.** 하나라도 빠지면 HTTP 500 이다.
  값은 비어도 된다. `users: {}`, `body: { mimeType, content: "" }`, 공백 한 칸 본문이 모두 통과했다.
  수정(`PUT`)은 제목만 보내도 통과해 이 제약이 없다.
- **수정의 `users` 는 객체 통째로 바뀐다.** to 에 나만 있던 일정에 `users: { cc: [나] }` 만 보내자 to 가 비었다.
  공식 문서의 "빈 값이 아닌 필드만 반영" 은 `users` 안의 `to`·`cc` 단위로는 적용되지 않는다.
- **같은 사람을 `to` 와 `cc` 에 함께 넣으면 `cc` 쪽이 빠진다.** `to: [나], cc: [나]` 를 보내자 to 에만 남았다.
  `cc: [나]` 만 보냈을 때는 cc 에 남았으므로 서버가 한 사람을 한 번만 두고 to 를 앞세우는 것으로 보인다.
  다른 사람을 넣어 확인하면 초대가 나가므로 본인으로만 확인했다.
- **반복 일정 회차 id 로 수정하면 남은 회차 전체가 바뀐다.** `<id>-20261109T000000Z` 로 `PUT` 하자 그 회차만이 아니라
  이후 회차가 모두 바뀌었다. 같은 회차 id 로 상세 조회(`GET`)와 `this` 삭제는 그 회차 하나에만 적용됐다.
- **`bymonthday` 는 쉼표 목록을 받는다.** `monthly` + `byday TH` + `bymonthday 18,19,20,21,22,23,24` 가
  "매월 18-24일 사이의 목요일" 로 전개됐다.
- **날짜만 준 `until` 을 `23:59:59+지역 offset` 으로 넓힌 값이 그대로 저장되고, 마지막 날의 회차까지 포함된다.**
  응답의 `recurrenceRule` 에는 `count`, `bysetpos`, `wkst` 같은 필드도 있다. 이번에는 다루지 않는다.
- **본문 `mimeType` 은 보낸 값 그대로 저장된다.** `text/x-markdown` 과 `text/html` 둘 다 받았다.
  웹은 `**굵게**` 를 두 형식 모두에서 굵게 그렸다.
- **알림과 비공개는 웹에서 적용을 확인했다.** `--alarm 10m` 은 "앱 10분 전", `--private` 는 "비공개" 로 보였다.
  상세 응답에는 `personalSettings` 가 나오지 않아 API 로는 확인할 수 없다.
- **`personalSettings` 를 보내지 않은 일정에는 캘린더 기본 알림이 붙는다.** 알림 없이 만든 종일 일정에
  "앱·메일 하루 전 12시" 가 걸려 있었다. 서버가 캘린더 설정의 기본 알림을 채우는 것으로 보인다.
- **일반 일정을 종일로 바꾸면 알림이 지워진다.** 10분 전 알림이 있던 일정을 `--start <날짜>` 로 종일 전환하자 웹에서 알림이 비었다.
  제목만, 시각만, 참석자(`--to`·`--cc`)만 수정한 일정은 알림과 수락 상태가 그대로 남았다.
  CLI 는 이 수정에서 알림을 다시 싣지 않는다. 전환할 때 알림이 필요하면 `--alarm` 을 함께 준다.
- **수정의 `personalSettings` 도 통째로 바뀐다.** 비공개에 10분 전 알림이 있는 일정 셋을 두고 웹에서 확인했다.
  `--alarm 30m` 만 보내자 알림은 30분 전이 됐지만 공개로 바뀌었다. `--private` 만 보내자 비공개는 남았지만 알림이 사라졌다.
  제목만 고친 대조 일정은 둘 다 그대로였다.
- **수정의 `recurrenceRule` 도 통째로 바뀐다** (2026-10-20). `monthly`, 간격 2, `byday TH`, `bymonthday 18,...,24`,
  `until 2027-06-30` 인 반복 일정에 `recurrenceRule: { frequency: monthly, interval: 1, until: 2027-08-31 }` 을 보내자
  상세 응답의 규칙이 간격 1, `byday`·`bymonthday` 빈 값으로 바뀌었다. 보내지 않은 필드는 기존 값이 남지 않는다.
  상세 응답에는 쓰기 요청과 같은 필드에 `count`·`bysetpos`·`wkst` 등이 더해져 오고, 없는 값은 `null` 이다.
- **반복이 아닌 일정의 상세 응답에는 `recurrenceRule` 키가 없다** (2026-10-23). 10월 일정 66건 가운데 `recurrenceType` 이 `none` 인
  44건에서 캘린더 두 곳의 일정을 하나씩 상세 조회했고, 둘 다 키가 없었다. 필드가 모두 `null` 인 객체는 오지 않았다.
  그래서 삭제의 `recurrenceRule != null` 판정은 반복이 아닌 일정을 반복 일정으로 보지 않는다 (Issue #228).
- **종일 일정은 의도대로 저장된다.** `--start 2026-10-21` 은 `startedAt 2026-10-21+09:00`, `endedAt 2026-10-22+09:00` 으로
  저장되고 날짜별 조회에서 10-21 하루만 잡혔다. 이틀짜리, 일반 일정을 종일로 바꾸는 수정, 종일 일정의 날짜 수정도 정상이었다.
- **조직 멤버 이름 검색(`GET /common/v1/members?name=`)은 부분일치다.** 성 두 글자나 이름 가운데 두 글자로도 걸린다.
- non-TTY 에서 `--yes` 없는 삭제는 종료 코드 3 으로 선차단되고, 회차 `this` 삭제와 `--to me` 는 정상이었다.
  반복 일정의 원본 id 에 `--scope all` 을 주면 이후 회차까지 모두 지워졌다. 실측 일정 28건을 이 명령으로 정리했다.
- **반복 일정의 원본 id 에 `deleteType: this` 를 주면 반복 전체가 지워진다** (2026-10-20). 주간 5회차 일정의 원본 id 를
  `--scope` 없이 지우자 목록에서 5회차가 모두 사라지고 원본 id 상세 조회가 404 를 냈다.
  같은 조건에서 회차 id 에 `this` 를 주면 그 회차 하나만 지워졌다.

아직 확인하지 못한 것:

- 권한이 `view` 인 캘린더에 쓸 때 서버가 주는 응답.
- **반복 규칙의 `timezoneName` 이 `--start` 의 offset 과 다른 시간대일 때.** `timezoneName` 은 실행 장비의 시간대다.
  `--start` 의 offset 과 다른 시간대의 장비에서 만들면 `byday` 가 다른 요일로 풀릴 수 있다.
  offset 에서 IANA 시간대 이름을 역산할 수 없어 그대로 둔다.
- **수정 시 참석자 병합에서 주최자(`users.from`)는 싣지 않는다.** 주최자가 본인인 일정에서는 `users` 를 바꾼 뒤에도
  등록자가 유지됐다. 남이 주최한 일정은 확인하지 못했다.
- **서버가 `until` 의 offset 을 그대로 따르는지.** 수정에서 날짜만 준 종료일을 일정의 시간대로 넓혀 offset 을 붙여 보내지만,
  장비와 시간대가 다른 일정에서 마지막 날 회차가 들어가는지는 실측하지 않았다.
- **반복이 아닌 일정에 `recurrenceRule` 키가 없다는 것은 내 캘린더 두 곳의 두 건에서만 확인했다.** 구독 캘린더 같은 다른 종류는 보지 못했다.
  다른 종류에서 필드가 모두 `null` 인 객체가 오더라도 삭제의 `!= null` 판정은 지우지 않고 멈추는 쪽으로 틀린다.

**설계 결정**:

- **종일 여부는 `--start` 형식으로 정한다.** `YYYY-MM-DD` 면 종일, offset 붙은 ISO8601 이면 일반 일정이다.
  `--end` 는 `--start` 와 같은 형식이어야 하고, 섞으면 거부한다.
- **종일 일정의 `--end` 는 마지막 날을 포함한다.** 서버의 `endedAt` 은 그 날을 포함하지 않으므로(ADR-063 실측)
  CLI 가 하루를 더해 보낸다. 조회 표가 `endedAt - 1일` 을 마지막 날로 그리는 것과 짝이 맞는다.
  생성에서 `--end` 를 생략하면 시작과 같은 날 하루다. 수정에서는 생략할 수 없다(아래 「수정은 준 옵션의 필드만 보낸다」).
  날짜에 붙이는 offset 은 고정값이 아니라 그 날짜의 지역 offset 이다.
- **일반 일정은 `--end` 가 필수이고 시작보다 뒤여야 한다.** 길이 0 인 일정도 받지 않는다.
- **입력 오류는 API 호출 전에 막는다.** offset 없는 일시, 실재하지 않는 날짜·시각, 순서가 뒤집힌 범위,
  알림 표기 오류, `--repeat` 없는 반복 부속 옵션은 config 를 읽기 전에 `EXIT_PARAM_ERROR` 로 끝낸다.
  서버는 날짜 형식을 검증하지 않고 500 을 낸다(ADR-063).
- **본문 기본 `mimeType` 은 `text/x-markdown` 이다.** 공식 예시는 `text/html` 이지만 서버는 둘 다 받고,
  CLI 사용자와 에이전트가 쓰는 본문은 대개 markdown 이다. 업무 생성의 기본값과도 맞춘다.
- **생성은 `users`·`body` 를 항상 싣는다.** 참석자가 없으면 `users: {}`, 본문이 없으면 기본 `mimeType` 과 `content: ""` 다.
  빠지면 서버가 500 을 내기 때문이다. 요청 조립 함수가 생성·수정 모드를 받아 이 차이를 한 곳에서 처리하므로
  `--dry-run` 출력도 실제로 보낼 본문과 같다. 수정은 이 제약이 없어 준 것만 싣는다.
- **수정에서 `--to`·`--cc` 중 한쪽만 주면 상세를 조회해 다른 쪽을 기존 값으로 채운다.** 서버가 `users` 를 통째로 바꾸므로
  `--cc` 만 고치려다 참석자가 모두 빠지는 사고를 막는다. 기존 항목은 종류에 맞게 옮긴다.
  `member` 는 `organizationMemberId` 만, 조직 밖 참석자인 `emailUser` 는 `emailAddress`·`name` 을 그대로 싣는다.
  옮길 수 없는 종류나 식별자가 빠진 항목이 있으면 조용히 빼지 않고 오류로 멈춘다.
  상세 조회 결과나 그 안의 `users` 가 비어 기존 참석자를 읽지 못해도 빈 목록으로 채우지 않고 멈춘다.
  둘 다 주면 조회하지 않고 준 목록으로 바꾼다. `--dry-run` 도 같은 조회를 해서 실제 보낼 본문을 보여준다.
- **수정에서 `--repeat` 을 주면 상세를 조회해 반복 규칙의 빈 세부 필드를 기존 값으로 채운다.** 서버가 `recurrenceRule` 을
  통째로 바꾸므로(실측) `--repeat monthly --repeat-until <날짜>` 로 종료일만 늦추려다 간격과 요일 조건이 지워지는 일을 막는다.
  `--repeat-until` 을 주지 않은 수정이 종료일을 지워 끝없는 반복이 되는 일도 같은 이유로 막는다.
  채우는 필드는 CLI 가 받는 `interval`·`until`·`byday`·`bymonth`·`bymonthday` 이고, 주기가 기존과 같을 때만 채운다.
  주기가 바뀌면 기존 세부 값이 새 주기와 맞지 않을 수 있어 채우지 않고, 지워질 필드를 stderr 로 알린다.
  단 `until` 은 주기와 상관없는 값이라 주기가 바뀌어도 채운다. 처음에는 함께 지웠는데, 주기만 바꾼 수정이 종료일을 지워
  반복이 끝없이 이어지는 문제가 있어 바꿨다 (Issue #228).
  기존 규칙에 CLI 가 다루지 않는 `count`·`bysetpos` 같은 값이 있으면 그것도 지워진다고 알린다.
  `timezoneName` 은 주기와 무관하게 기존 값을 둔다. 반복을 펼치는 기준은 일정에 속하므로, 다른 시간대 장비에서 고쳐도 요일이 옮겨지지 않는다.
  날짜만 준 `--repeat-until` 도 그 `timezoneName` 기준 23:59:59 로 다시 넓힌다. 장비 시간대로 넓히면 일정의 시간대에서
  마지막 날 회차가 빠지거나 다음 날 회차가 들어간다 (Issue #237). offset 은 Node 의 `Intl` 로 그 날짜의 값을 구한다.
  주기는 대소문자를 맞춰 비교한다. 실측 응답은 소문자였다.
  참석자 병합과 조회를 한 번으로 묶고, `--dry-run` 도 채운 규칙을 보여준다. 지워질 필드 경고는 스피너를 멈춘 뒤에 낸다.
  실제 수정에서는 경고가 수정이 끝난 뒤에 나오므로, 경고에 필드 이름만 두면 지워진 값을 되살릴 정보가 없다.
  그래서 CLI 옵션이 있는 필드는 원래 값을 붙인 옵션(`--repeat-byday TH`)으로, 없는 필드는 `count=10` 처럼 값으로 함께 알린다 (Issue #228).
  `--repeat-*` 는 `--repeat` 없이 받지 않으므로 이번에 보낸 빈도를 앞에 붙여 그대로 다시 실행할 수 있게 한다.
  스킬 문서에 「먼저 `--dry-run`」 을 적는 안은 에이전트가 그 문장을 지켜야만 효과가 있어 기각했다.
- **수정은 반복 일정 회차 id 를 API 호출 전에 거부한다.** id 끝이 `-YYYYMMDDTHHMMSSZ` 이면 회차로 보고 `EXIT_PARAM_ERROR` 로 끝낸다.
  회차 하나만 고칠 수 없고 반복 전체가 바뀐다는 것, 전체를 고치려면 원본 id 로 다시 부르라는 것을 원본 id 와 함께 알린다.
  삭제는 회차 단위로 동작하므로 회차 id 를 그대로 받는다.
- **캘린더는 id 나 이름으로 받는다.** 15자리 이상 숫자는 id 로 그대로 쓰고, 그 밖은 캘린더 목록에서
  정확일치 → 부분일치 → 모호하면 후보 목록 순으로 찾는다. 구독 캘린더(`subscription`)는 외부에서 가져온 읽기 전용이라
  이름 후보에서 뺀다. id 로 직접 주면 종류를 확인하지 않고 서버 판정에 맡긴다.
- **참석자는 조직 멤버만 받는다.** 각 값은 organizationMemberId, 이메일, 이름, `me` 다.
  id 와 이메일은 기존 `resolveMemberByIdOrEmail` 로 풀고, 조직에 없는 이메일은 `emailUser` 로 보내지 않고 거부한다.
  오타 난 주소나 외부 주소로 초대 메일이 나가면 되돌릴 수 없다.
  이름은 프로젝트 스코프가 없으므로 조직 전체 이름 검색을 쓰고, 검색이 부분일치라(실측) 결과에서 **정확일치만** 인정한다.
  0건이면 거부하고, 동명이인이면 이름과 id 를 나열하고 거부한다. 검색은 100건씩 5쪽까지 넘겨 보고, 넘으면 id·이메일을 요구한다.
  마지막 쪽은 응답의 `totalCount` 로 판단하고, `totalCount` 가 없으면 100건보다 적게 온 쪽을 마지막으로 본다.
  처음에는 `totalCount` 가 없으면 첫 쪽에서 끝내 다음 쪽의 동명이인을 놓칠 수 있었다 (Issue #228).
  공식 문서는 `size` 의 최댓값을 100 으로, 응답의 `totalCount` 를 필터 조건에 맞는 전체 건수로 적는다(2026-10-22 확인).
  쪽 크기 100 은 그 최댓값이고, `totalCount` 가 없을 때의 판단은 문서와 다른 응답이 올 때를 대비한 것이다.
  상한까지 정확일치를 찾았어도 고르지 않는다. 보지 못한 쪽에 같은 이름이 더 있을 수 있기 때문이다.
  대신 찾은 후보의 이름과 id 를 오류에 함께 보여 id 로 바로 다시 실행할 수 있게 한다.
- **알림은 `[mail:|app:]<n><m|h|d|w>` 로 받는다.** `10m` → `TRIGGER:-PT10M`, `mail:1d` → `TRIGGER:-P1D`.
  `action` 을 생략하면 `app` 이다. 알림과 `--private` 은 `personalSettings` 로 보내고, 둘 다 없으면 그 키를 만들지 않는다.
  `busy` 는 다루지 않는다.
- **수정에서 지워질 개인 설정은 stderr 로 알리고 진행한다.** `personalSettings` 는 통째로 바뀌는데 상세 응답에 없어
  `users` 처럼 기존 값을 채울 수 없다. `--alarm` 만 주면 공개로 바뀐다고, `--private` 만 주면 알림이 지워진다고,
  알림 없이 날짜만 준 `--start` 면 종일 전환으로 알림이 지워진다고 알린다. 기존 일정이 일반인지 비공개인지는 모르므로
  그럴 수 있다는 조건부 경고다.
- **반복은 `--repeat <빈도>` 와 부속 옵션으로 받는다.** `timezoneName` 은 실행 장비의 시간대다.
  `byday` 는 표기가 여럿이라 그대로 넘긴다. `bymonth`·`bymonthday` 는 쉼표 목록을 받고, 각 값을 문서의 범위(1-12, 1-31)로
  검증한 뒤 공백 없이 `18,19,20` 형태로 보낸다. 빈 항목은 거부한다. 서버가 목록을 전개하므로(실측)
  정기점검 같은 "매월 18-24일 사이 목요일" 을 `--repeat monthly --repeat-byday TH --repeat-bymonthday 18,19,20,21,22,23,24` 로 만들 수 있다.
- **날짜만 준 `--repeat-until` 은 그 날 `23:59:59` 지역 시각으로 넓힌다.** 그 날의 회차까지 포함된다(실측).
- **수정은 준 옵션의 필드만 보낸다.** 시각은 기존 값을 조회하지 않으므로 일반 일정과 종일 일정 모두 `--start` 와 `--end` 를 함께 줘야 한다.
  종일에서 `--end` 생략을 생성처럼 하루로 보면 사흘짜리 일정의 시작일만 옮기려던 수정이 기간까지 하루로 바꾸고,
  그 변화가 출력에도 드러나지 않는다. 하루 일정은 `--end` 에 같은 날짜를 준다. 시각을 바꿀 때는 `wholeDayFlag` 도 함께 보낸다.
  요청에 실을 필드가 하나도 없으면(`--mime-type`·`--dry-run` 만 줬거나 `--body ""` 처럼 값이 빈 경우) 거부한다.
- **본문 없이 `--mime-type` 만 주면 stderr 로 알리고 무시한다.** 생성의 빈 본문에는 기본 `mimeType` 을 쓴다.
- **`--dry-run` 은 이름 해석까지 한다.** 캘린더와 참석자 이름이 맞게 풀리는지가 미리보기의 핵심이라 조회 API 는 부른다.
  쓰기 API 만 부르지 않고 요청 본문 JSON 을 낸다.
- **삭제는 ADR-036 규약을 따른다.** 확인을 기본으로 하고 `-y`/`--yes` 로 생략하며, non-TTY 에서 `--yes` 가 없으면
  config·resolver·API 호출 전에 끝낸다. 확인 문구에 제목과 시각을 보여주려고 상세를 조회하는데, 이 조회는 확인 단계 안에서만
  일어나므로 선차단 순서를 깨지 않는다. `--scope this|from-this|all` 을 `deleteType` 의 `this|wholeFromThis|whole` 로 옮긴다.
- **반복 일정의 원본 id 에 `this` 범위면 확인을 묻기 전에 거부한다.** 서버는 이 조합으로 반복 전체를 지우는데(실측)
  `--scope` 기본값이 `this` 라, 생략한 삭제가 시리즈를 통째로 지운다. 회차 id 형태가 아닌 id 에 `this` 범위면 상세를 조회해
  `recurrenceRule` 이 있으면 `EXIT_PARAM_ERROR` 로 끝내고, 회차 id 와 `--scope all` 을 안내한다.
  `-y` 로 확인을 건너뛰어도 API 전에 같은 판정을 한다. 판정은 상세 응답으로만 할 수 있어 조회가 실패하면 지우지 않는다.
  TTY 확인에서는 이 조회 결과를 확인 문구에도 쓴다. 회차 id 와 `from-this`·`all` 은 조회하지 않는다.
  회차 id 의 `this` 확인 문구에는 「이 회차만 지웁니다」 를 붙인다.

**대안 기각**:

- **`--alarm`·`--private` 중 하나만 준 수정을 거부하기** — 공개 일정의 알림만 바꾸는 흔한 수정까지 막는다.
  기존 값을 모르는 상태에서 거부하면 사용자가 원래 공개였던 일정에 `--private` 를 붙여 오히려 설정을 바꾸게 된다.
- **`--public` 을 만들어 class 를 항상 싣기** — 결과가 결정적이 되지만 비공개 일정의 알림을 고칠 때 공개로 바꾸는 것은 그대로다.
  경고로 알리는 것과 지키는 범위가 같고 옵션만 늘어난다.

- **참석자 이름을 받지 않기 (`messenger send` 방식, ADR-033)** — 메신저는 한 사람에게 보내는 명령이라 id·이메일만 받아도
  부담이 작다. 일정은 여러 사람을 한 번에 넣는 일이 흔해서 사람마다 id 를 찾게 하면 쓰기 어렵다.
  조직 전체 검색의 정확일치만 인정하면 잘못된 사람을 넣을 위험이 부분일치보다 작고, 동명이인은 오류로 드러난다.
- **이름 부분일치 허용** — 프로젝트 resolver 와 달리 후보가 조직 전체라 부분일치 하나가 엉뚱한 사람일 가능성이 크다.
  일정 초대는 상대에게 알림이 가므로 틀린 해석의 비용이 크다.
- **검색 상한까지 찾은 정확일치가 한 명이면 그 사람 쓰기** — 한때 이렇게 구현했다. 사람이 분명히 있는데 오류가 나는 불편은 줄지만,
  6쪽 이후의 동명이인을 보지 못한 채 앞쪽 사람에게 초대가 나간다. 후보를 오류에 보여주면 불편도 대부분 사라진다.
- **반복 규칙의 `count`·`bysetpos` 같은 필드도 기존 값을 다시 싣기** — 서버가 그 필드를 쓰기 요청에서 받아
  같은 뜻으로 저장하는지 실측하지 않았다. 지워진다고 알리고, 필요하면 웹에서 고치게 한다.
- **`--all-day` 플래그로 종일 지정** — 플래그와 값 형식이 어긋나는 조합(`--all-day --start 2026-09-18T10:00:00+09:00`)을
  따로 정의해야 한다. 형식으로 정하면 조합이 생기지 않고, 서버도 종일 일정을 시각 없는 형식으로 구분한다.
- **일반 일정의 `--end` 기본값(+1시간)** — 회의 길이는 일정마다 달라 기본값이 맞는 경우가 많지 않다.
  잘못된 길이로 만들어진 일정은 참석자 캘린더에 그대로 퍼진다. 명시를 요구한다.
- **`edit` 의 `$EDITOR` 폴백** — `post edit` 은 본문 하나를 고치는 명령이라 편집기가 맞지만, 일정 수정은 제목·시각·참석자처럼
  필드가 여럿이다. 옵션 없이 실행하면 편집기를 열지 않고 수정할 항목이 없다고 알린다.
- **수정 전 기존 값을 조회해 시각 길이 맞추기** — `--start` 만 줘도 기존 길이를 유지할 수 있지만 호출이 하나 늘고
  기존 일정의 종일 여부까지 따져야 한다. 길이를 몰래 맞추면 결과를 예측하기도 어렵다. 일반·종일 모두 둘 다 요구한다.
- **조직 밖 이메일을 `emailUser` 로 보내기** — 공식 문서는 받지만, 이메일 오타가 외부 초대로 이어진다.
  필요해지면 명시 옵션으로 연다. 수정에서 기존 `emailUser` 를 그대로 옮겨 싣는 것은 새로 초대하는 것이 아니라 유지하는 것이다.
- **원본 id 의 `this` 삭제를 확인 문구로만 알리기** — `-y` 나 에이전트 실행에서는 문구를 읽는 사람이 없다.
  한 회차를 지우려던 삭제가 반복 전체를 지우고, 지운 일정은 되돌릴 수 없다.
- **회차 id 수정을 경고만 하고 진행** — 사용자는 회차 하나를 고치려 했는데 남은 반복 전체가 조용히 바뀐다.
  참석자에게도 바뀐 일정이 퍼지고, 회차별로 되돌릴 방법이 없다. 경고는 스크립트나 에이전트 실행에서 읽히지 않는다.
- **한쪽 참석자 덮어쓰기를 문서에 주의로만 적기** — 문서를 읽지 않은 호출은 참석자를 잃는다. 손실이 조용하고
  일정 상세를 다시 열어야 알아챌 수 있다. 상세 조회 한 번으로 막을 수 있으므로 CLI 가 채운다.
