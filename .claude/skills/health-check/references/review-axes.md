# 구조와 유지보수성 검토 축

4단계에서 검토 에이전트 둘에게 나눠 준다. 두 검토자의 범위가 겹치지 않게 서로의 축을 알려 준다.
둘 다 읽기 전용이다. 파일을 고치지 말라고 적는다.

## 공통으로 주는 것

- 먼저 읽을 문서: `CLAUDE.md`, `docs/code-architecture.md`, `docs/adr/INDEX.md`
- 1단계의 `conventions.md` 전문. 이미 센 항목은 다시 세지 말고 원인과 제안만 더하게 한다
- 결과 형식: 한국어, 심각도(높음, 중간, 낮음), 근거 파일과 줄, 제안, 이득과 비용을 담은 표. 추측이면 추측이라고 표시한다. 잘 된 점도 짧게 적는다
- 표 한 줄에는 항목 하나만 적고, 설명은 근거와 제안만 남긴다

## 검토자 A: 구조

| 축 | 볼 것 |
| --- | --- |
| 레이어 경계 | `docs/code-architecture.md` 의 의존 방향을 실제 import 가 지키는지. grep 한 결과를 근거로 댄다 |
| 명령 간 중복 | 입력 해석, `--json` 과 `--quiet` 출력, 확인 프롬프트, 오류 처리가 명령마다 따로 구현됐는지 |
| 규약과 동작의 일치 | `CLAUDE.md` 「명령 공통 규약」 의 입력 형식을 모든 대상 명령이 받는지. 가능하면 빈 HOME 에서 빌드한 CLI 를 실행해 종료 코드로 확인한다 |
| 큰 파일 | 나누는 것이 이득인지, 반복을 줄이는 것이 먼저인지. 테스트 mock 을 얼마나 고쳐야 하는지까지 비용에 넣는다 |
| 시작 시간 | `dooray --version` 실측과 무거운 import 의 기여분 |

## 검토자 B: 유지보수성

| 축 | 볼 것 |
| --- | --- |
| 타입 | `tsconfig.json` 의 strict 계열 옵션, 켰을 때 늘어나는 오류 수, `as` 단언과 `!` 의 위치, 판별 유니온이 필요한 곳 |
| 인터페이스 계약 | API 응답을 런타임 검증 없이 믿는 곳, "없음" 을 `null`, `undefined`, throw 중 무엇으로 나타내는지의 일관성, `--json` 이 raw 응답을 지키는지 |
| 오류 처리 | HTTP 오류, 네트워크 오류, timeout 이 어디서 `DoorayCliError` 로 바뀌는지, 종료 코드를 잃는 재포장, 조건 없는 `catch {}` |
| 민감 정보 | 설정과 캐시 파일 권한, 로그나 이슈 첨부에 토큰이 섞일 경로 |
| 그 밖의 영역 | 캐시 무결성과 동시 실행, 테스트 품질과 공백, CI 워크플로, 패키지 공개 범위, Windows 에서의 개발과 실행 |

## 결과를 받은 뒤

높음 항목은 근거로 든 파일과 줄을 직접 연다. 검토자가 실행으로 확인했다고 적은 항목은 그렇다고 보고에 적고, 다시 돌렸는지 여부도 적는다.
회신을 받고 더 물을 것이 없으면 그 검토자는 거기서 끝낸다.
