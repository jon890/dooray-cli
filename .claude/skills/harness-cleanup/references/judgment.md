# 판정 기준

기계로 잡을 수 없는 부분이다. 아래 네 가지로 문장 단위 판정한다.

## 1. 설명인가 지침인가

지침 파일에는 "무엇을 하라 / 하지 마라" 만 둔다. "무엇이 어떻게 동작한다" 는 `docs/` 로 보낸다.

| 판정 | 예 |
| --- | --- |
| 설명 — 옮기거나 지운다 | "스킬은 npm 패키지 경로를 직접 가리키지 않고 관리 저장소를 거쳐 연결된다" |
| 지침 — 남긴다 | "CLI 를 새 버전으로 설치했으면 `dooray skill update` 를 직접 실행한다" |

한 단락에 섞여 있으면 지침만 남기고 나머지를 지운다.
실제 사례로, tsup 과 tsc 의 역할을 설명하는 다섯 줄에서 지침은 "새 의존성을 추가하면 `exports` 맵 진입점을 확인한다" 한 줄이었다.

**예외**: 판단 근거가 되는 짧은 이유는 남긴다. 이유를 알면 변형 상황에서도 옳게 행동한다.
`"${SCAN[@]}"` 를 쓰는 이유(zsh 는 단어 분할을 하지 않고 bash 는 첫 원소로 축약한다)가 그 예다.
그 주석이 없으면 다음 사람이 문자열 변수로 되돌린다.

## 2. 애초에 하지 않을 일을 금지하고 있는가

최신 모델이 하지 않을 행동을 막는 지침은 자리만 차지한다.

지운 예를 보면 성격이 드러난다.

- "공식 문서 사본을 repo 에 두지 않는다" — 사본을 만들 이유가 없다
- "인증 문제가 아니므로 토큰을 붙여도 달라지지 않는다" — 원인을 정확히 적었으면 토큰을 시도하지 않는다
- "grep 명령을 여기에 복사하지 않는다" — 참조가 명확하면 복사할 이유가 없다
- "axios 사용 금지" — `ky` 를 쓰라고 적었으면 충분하다

**남기는 기준**: 실제로 그 실수가 일어난 기록이 있는가.
`--generate-notes` 를 쓰지 말라는 지침은 남긴다 — 그것을 쓰면 Closes 목록이 빠지고, 그 판단이 자명하지 않다.

## 3. 모델이 판단해도 되는 것을 규정하고 있는가

관례를 세세히 규정하면 문서만 늘고 어긋난다.

- 브랜치 명명 표와 PR 제목 형식 — 히스토리를 보면 판단할 수 있다
- 커밋 메시지 형식 — 같다

**남기는 기준**: 히스토리로 유추할 수 없는 프로젝트 고유 정책인가.
"커밋 메시지는 한국어로 작성한다" 는 남긴다 — 영문 커밋이 섞인 히스토리에서는 유추되지 않는다.

## 4. 개수와 목록을 문서에 박았는가

가장 자주 틀리는 유형이다. 실측한 사례가 이렇다.

| 대상 | 문서에 적힌 값 | 실제 |
| --- | --- | --- |
| 캐시 파일 목록 | 4개 문서가 각각 6 / 7 / 8 / 10개 | 10개 |
| ADR 목록 | `001~031` | `001~035` (4개 누락) |
| 입력 통합 명령 수 | 3개 문서가 16 / 17 / 19 | 19개 |
| pitfalls 파일 수 | 69개 | 당시 정확, 파일 하나 늘면 틀린다 |

**개수는 적지 않는다.** "N개" 는 지침의 힘을 더하지 않는다.
목록은 한 곳만 두고 나머지는 그 문서를 가리킨다.

## 공개 스킬의 독자는 에이전트다

사람용 문서와 기준이 다르다.

| 필요 | 불필요 |
| --- | --- |
| 명령 시그니처와 옵션 | 설치·시작 안내 (사용자가 이미 했다) |
| 판단 기준 — 언제 이 명령을 쓰는가 | 두 명령을 순서대로 실행하는 것뿐인 예시 |
| 함정 — 무엇이 직관과 다른가 | 내부 구현 방식 |
| 출력 스키마 — 무엇을 파싱하는가 | 기능 소개 |
| 되돌릴 수 없는 동작 | |

되돌릴 수 없는 동작은 특히 중요하다.
"reference 마다 다르니 확인하라" 는 안내로는 에이전트가 어느 삭제 명령이 즉시 실행되는지 알 수 없다. 표로 준다.
