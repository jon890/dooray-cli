# Phase 04 — SKILL.md 라우터와 references·templates 작성

**Execution profile**: standard

---

## 목표

스킬의 사람·모델이 읽는 부분을 만든다. 앞 phase 가 만든 스크립트를 어떤 순서로 어떤 판단과 함께 쓰는지가 여기 담긴다.

**범위 외**: README 안내와 패키지 범위 조정은 phase 05 다.

---

## 전제

phase 01~03 이 만든 스크립트가 있어야 한다. 문서가 스크립트 이름과 인자를 그대로 인용하므로 실제 파일과 대조하며 쓴다.

**신규 스킬을 만드는 작업이므로 `/skill-creator:skill-creator` 워크플로우를 따른다.**
초안을 쓴 뒤 테스트 프롬프트로 트리거와 동작을 확인하고, 결과를 보고 다듬는 순환을 거친다.

---

## 반드시 지킬 제약

이 저장소는 공개다. 그리고 이 스킬은 다른 회사 구성원도 그대로 쓸 수 있어야 한다.

- 조직·프로젝트·개인에 종속된 값을 문서에 넣지 않는다. 예시는 `my-project`, `user@example.com` 같은 가상 값만 쓴다
- `skills/` 아래에는 내부 추적 번호를 남기지 않는다. `ADR-037` 같은 참조는 금지다. 근거가 필요하면 사실 자체를 문장으로 쓴다
- 산출물 문서의 내용은 **하네스 중립**으로 쓴다. 경로 기본값만 Claude Code 관례를 따르고, 문서 본문이 특정 도구를 전제하지 않게 한다

## 작업 항목 (5)

### 1. `skills/dooray-persona/SKILL.md` — 신규 (라우터)

frontmatter 의 `name` 은 `dooray-persona` 다.

`description` 은 이 스킬의 유일한 트리거 장치다. 다음을 모두 담는다.

- 무엇을 하는지 — Dooray 에 쌓인 본인 글을 모아 업무 글 문체 문서를 만든다
- 트리거 표현 — "문체 페르소나", "내 글투 추출", "AI 티 안 나게", "업무 글 문체 분석" 같은 한국어 표현과 영어 대응
- **경계** — 업무·댓글 단건 조회·등록·수정은 `dooray-cli` 스킬이 맡는다. "업무 목록 보여줘" 같은 단순 조회로는 이 스킬을 쓰지 않는다

본문은 `dooray-cli/SKILL.md` 와 같은 라우터 형태로 짧게 유지한다. 담을 것은 다음과 같다.

- 어느 reference 를 언제 읽는지 표
- 6단계 워크플로우의 이름과 한 줄 요약
- 실측 함정 요약 (상세는 reference 로 넘긴다)
- 설치 방법 — 이 스킬은 CLI 설치 명령의 대상이 아니다. 저장소를 내려받아 `skills/dooray-persona` 를 `~/.claude/skills/` 로 링크하거나 복사해서 쓴다
- 설정 파일 위치와 최초 1회 수집 흐름

500줄을 넘기지 않는다. 상세는 reference 로 내린다.

### 2. `skills/dooray-persona/references/collection.md` — 신규

1단계(대상 탐색)와 2단계(수집)의 상세다.

- `discover-targets.mjs` 실행법과 후보 표를 사용자에게 어떻게 보여주고 고르게 하는지
- 고른 결과를 설정 파일에 어떻게 저장하는지. 설정에 대상이 이미 있으면 탐색을 건너뛴다
- `collect.mjs` 실행법과 재수집 판단
- **API 함정 세 가지를 이유와 함께** 남긴다. 재발견 비용이 크다
  - 담당자가 팀 그룹으로 걸린 업무를 놓치면 대외 회신 표본이 통째로 사라진다. 실측한 한 프로젝트에서 개인 담당은 1건이었고 그룹 담당까지 세면 254건이었다
  - 초당 5회를 넘기면 오류가 아니라 빈 결과가 온다. 수집이 조용히 비므로 속도 제어를 반드시 공유해야 한다
  - 목록 응답에는 본문이 없다. 작성자·담당자는 들어 있으니 후보를 먼저 로컬에서 좁혀 호출을 줄인다

### 3. `skills/dooray-persona/references/classification.md` — 신규

3단계(AI 작성분 분리) 상세다.

- 신호별 의미와 라벨 판정 순서
- **정형 양식을 AI 로 분류하면 안 되는 이유** — 헤더·표가 많다고 AI 로 본 것들이 실제로는 사람이 쓴 배포 기록이었다. 정형 양식은 표본에서 빼되 AI 집계에 넣지 않는다
- 사용자 확인 절차 — `--report` 로 나온 경계 항목을 사용자에게 보여 라벨을 확정받는다. 확인 없이 다음 단계로 넘어가지 않는다
- 세션 로그 대조는 **선택 기능**이다. 있으면 정확도가 오르고 없으면 건너뛴다

### 4. `skills/dooray-persona/references/authoring.md` — 신규

4·5·6단계 상세다.

**4단계 — 문체 추출.** 모델이 `human` 표본을 직접 읽고 규칙을 뽑는다. `stats.mjs` 결과는 근거 보강용이지 결론이 아니다.

- 수신자 축을 **표본에서 찾는다.** 두 모드로 갈리는 것이 흔한 결과지만 사람마다 다르므로 축을 미리 고정하지 않는다
- 뽑을 것 셋 — 수신자별 모드, 반복 습관, 하지 않는 것
- 표본이 적으면 임의 임계값으로 중단하지 말고 표본 수를 보고해 사용자가 계속할지 정하게 한다

**5단계 — 문서 생성.** `templates/persona.md` 골격으로 설정의 `outputPath` 에 쓴다.

**6단계 — 주입과 연동.** 만든 문서를 실제로 쓰이게 하는 단계다. 이게 빠지면 문서가 파일로만 남는다.

- 문서를 규칙 파일로 두고 하네스가 매번 읽게 연결하는 방법. Claude Code 는 `CLAUDE.md` 에서 그 파일을 참조하는 한 줄을 더하면 된다. 다른 하네스는 규칙 파일 첨부나 시스템 프롬프트 추가로 같은 효과를 낸다
- `dooray-cli` 스킬과의 연동 — Dooray 댓글·업무를 등록하기 전에 이 문서의 모드 판정과 자가 점검을 먼저 통과시킨다. 등록 전 미리보기를 보여주는 지점이 자가 점검을 끼워 넣을 자리다
- 주입한 뒤 확인하는 법 — 짧은 댓글을 하나 써 보게 하고 자가 점검 항목과 대조한다

### 5. `skills/dooray-persona/templates/persona.md` — 신규

생성될 문서의 골격이다. 다음 절을 둔다.

- 이 문서가 무엇이고 무엇을 근거로 만들어졌는지 — 표본 수와 수집 기간을 채우는 자리
- 수신자별 모드 — 모드마다 특징과 실제 예시가 들어갈 자리
- 두 모드에 공통인 습관
- 하지 않는 것
- **기존 문체 규칙과의 관계** — 이 절은 비워 두지 말고 반드시 채우게 안내한다
  - 페르소나가 기존 규칙을 덮어쓰지 않는다. 기존 규칙을 통과한 뒤 그 안에서 개인 색을 살린다
  - 충돌해 보이는 지점을 찾아 어느 쪽이 우선인지 적는다. 예를 들어 일반 문서 규칙이 평문의 명사형 종결을 금지하는데 개인 작업 로그는 항목 나열이라 명사구가 기본인 경우가 있다. 이때 그것이 규칙 위반이 아니라 목록 항목 예외에 해당한다는 점을 밝힌다
- 자가 점검 목록
- 문서 끝에 **주입 스니펫** — 사용자가 복사해 하네스 설정에 붙일 수 있는 한두 줄

## 의도 메모 (왜)

- SKILL.md 를 라우터로 두는 이유는, 트리거 시 본문 전체가 컨텍스트에 올라가기 때문이다. 단계별 상세를 본문에 쌓으면 쓰지도 않을 내용을 매번 읽는다.
- 수신자 축을 고정하지 않는 이유는, 두 모드로 갈린 것이 한 사람의 실측 결과이지 일반 법칙이 아니기 때문이다. 축을 박으면 다른 사용자의 표본을 그 틀에 억지로 끼워 맞춘다.
- 6단계를 따로 둔 이유는, 문서를 만들어 놓고 쓰지 않는 것이 이 워크플로우의 가장 흔한 실패이기 때문이다.
